自動測試工具Unity-Autorun-Tool的演進(2026)

發表於 2026-08-12 分類於 AI技術 閱讀次數：

2024 年底，我做了一個很小的 Unity 自動點擊工具：之前每次進遊戲都要等待場景加載，再依次點幾個連接、登錄和進入遊戲的按鈕。這段流程大約持續半分鐘，操作不復雜，卻要我一直盯著，並不是很方便。

後來隨著AI技術的發展，感覺這一套自動工具如果給AI做為腳手架會大有可為。因此逐步增加了 UI 導航、編輯器入口和命令行調用接口。正式以一個AI Agent MCP為目標交付。

最初我只想把這些點擊交給預設。後來要自測的界面越來越多，現在可以先準備好界面之間的路徑，日常調試時直接選擇目標，讓程序完成中間的導航。

裁取自 README 中的實際界面截圖，保留窗口上部並隱藏進程 ID；點擊圖片可打開項目倉庫。

第一版只處理固定步驟

初版在 2024 年 11 月完成基本功能，隨後補充退出前的動作和使用說明。一個預設保存一組順序操作，每項主要包含：

字段 作用
按鈕名稱 定位要操作的對象
按鈕文字 必要時輔助區分同名按鈕
等待時間 等待場景或界面準備完成
UI 框架 選擇 UGUI 或 FairyGUI 的處理方式

運行工具之後，進入 Play Mode，再按順序執行配置。後來增加的 Stop 動作則在停止運行之前執行，例如先退出當前房間，再結束調試。

這版工具沒有縮短遊戲自身的加載時間。它省掉的是等待期間必須由人完成的幾次操作，讓我能夠在加載時去做別的事情。

同一套機制後來用於幾個不同工程。項目之間的登錄流程雖然不一樣，但只要調整預設，就不必為每個工程再寫一套編輯器按鈕。

從操作序列到界面關係

順序預設適合固定入口，界面變多之後卻會暴露兩個問題。

第一，多個目標會共享前半段流程。例如打開背包與打開設置都要先進入主界面，為每個目標複製一份完整序列，會讓登錄流程的改動傳播到很多預設。

第二，執行起點不一定相同。有時還未進入 Play Mode，有時已經在主界面，有時正停在一個彈窗裡。只有一串按鈕名稱，很難表達這些差異。

因此我開始用導航圖描述 UI，把信息拆成界面、控件、跳轉和路由：

概念 記錄的內容
View 一個可以識別的界面或面板
Control 導航需要操作的按鈕等控件
Transition 從某個界面到另一個界面的操作關係
Route 一條可複用的導航路徑

簡化示意，界面名稱與具體項目無關。共享的登錄流程只需要維護一次。

圖裡的一條邊也不能只寫“主界面可以打開背包”。還要知道通過哪個控件執行、到達後用什麼條件確認，以及在當前環境下是否具備執行前提。

靜態代碼裡存在一次打開界面的調用，說明存在可達關係，但不代表自動化工具馬上就能走通。例如入口可能受等級條件限制，或者必須先完成一次異步操作。這些缺口需要保留下來，不能當作已經驗證的路徑。

AI 參與準備，日常導航由程序執行

項目裡有很多 UI 調用，手工整理完整導航圖本身也有成本。我讓 AI 輔助分析源碼中的界面關係，把候選整理成導航數據，再根據工具能夠識別和執行的條件進行檢查。

這裡把兩類工作分開：

  • 準備階段理解代碼與界面語義，生成或修訂導航圖。
  • 執行階段讀取已準備的圖，運行確定的步驟，等待結果並報告狀態。

路徑已經具備後，點擊編輯器按鈕或通過命令行運行，不需要再讓模型為每一步重新做決定。這裡說的“離線導航”是指執行過程不依賴 AI 推理，遊戲本身仍然可能需要連接服務器。

這也給維護劃出了範圍：界面結構或跳轉邏輯改動時更新相應數據；沒有變化的路徑繼續複用。導航圖是一份需要隨項目維護的工具數據，並不是生成一次就永遠有效。

點擊完成與導航完成是兩件事

早期順序預設主要依賴等待時間，但固定延遲有明顯侷限。機器負載、資源緩存和網絡響應變化後，同樣等兩秒可能太短，也可能白等很久。

導航執行更適合圍繞狀態組織：

發送點擊只代表執行過操作，不代表目標面板已經打開。反過來，某個 GameObject 已經存在，也未必表示界面已經可見、可交互。到達判定必須與 UI 的實際生命週期對應。

長流程還需要能被取消，並有明確的運行中、完成和失敗狀態。否則一旦卡在中間，使用者只能猜測是在等資源、沒有找到按鈕，還是某個前置條件沒有滿足。

編輯器入口與外部入口共用執行能力

工具後來通過本地 HTTP Bridge 暴露 Unity 內部操作，再由獨立的 MCP Server 對接外部客戶端。編輯器面板與外部入口最終使用同一套操作能力，不需要各自維護一套點擊邏輯。

這個邊界也有實際意義：網絡請求處理與 Unity 對象訪問處在不同的執行環境，訪問場景對象、UI 和編輯器狀態的部分仍然需要回到 Unity 主線程。Bridge 負責把請求交給合適的執行位置，再把結果返回出去。

進入 Play Mode 也不是一個瞬間完成的調用。執行任務需要跨過模式切換和初始化過程，所以外部調用更適合啟動一個任務，再查詢它的進度，而不是讓一次同步請求無限等下去。

普通開發者未必需要了解這些接口。日常使用時，在窗口裡搜索目標界面並運行就夠了；外部接口則給批量調試和進一步的自測留下入口。

接入與使用

工具提供 UPM 安裝入口、編輯器內的 Bridge 與 MCP 管理，以及運行時 UI 狀態讀取，可以從編輯器面板完成接入，再執行導航和狀態檢查。

到達之後檢查 UI 狀態

導航與斷言能夠證明什麼

這套工具在我日常工作中最常用的場景，仍然是快速進入遊戲併到達待調試界面。它減少的是操作路徑上的重複勞動。

到達界面之後，按鈕狀態、數據正確性、動效以及網絡行為仍然需要各自的驗證。導航成功不能直接等同於功能測試通過，也不能證明所有設備上的視覺表現都正確。

運行時斷言把“到哪裡”和“到了之後檢查什麼”分別交給路由與狀態條件。這樣頁面入口變動時只修改導航，業務判斷也可以獨立維護；但控件文本與狀態符合條件，仍然不能直接證明動效和所有設備上的視覺表現都正確。

從第一版自動點擊到後來的導航圖，需求始終來自重複發生的小操作。先把最穩定的部分配置化，再隨著使用範圍擴大補充狀態和外部接口，比一開始就規劃完整測試平臺更符合這次工具的演進過程。
