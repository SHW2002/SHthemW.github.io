Improving the EmmyLua (LuaLS) Unity API Annotation Generator

Posted on 2025-03-27 In 游戏开发 Views:

Calling C# from Unity’s Lua code works at runtime, yet the editor may lose field hints through singletons, delegates, or the CS table.

I extended an open-source generator to restore them.

These changes ran from January through March 2025 and were eventually merged upstream through a pull request. This article records several of the most useful improvements.

The tool’s GitHub README; click the image to open the repository.

Generate annotations without changing the runtime

The tool uses reflection in the Unity editor to inspect C# assemblies, then generates type declarations that a Lua language service can understand. These files are for editor analysis and should not be loaded as executable business scripts.

Where generic inheritance loses type information

The most common example is a generic singleton:

If the generator only examines the generic definition, it can only declare Instance as T. For InventoryService, however, inheritance already supplies the type argument: the editor could know that Instance is an InventoryService.

I added a check of the base class’s generic information when generating a concrete derived class, resolving known field and property types into that class’s declaration. The type chain can then continue through InventoryService.Instance.Capacity.

This is not a complete C# generic inference system. At this stage, the implementation mainly covers non-generic derived classes, a direct base class with one generic parameter, and inherited fields and properties. Multiple-parameter mappings, complex nesting, and generic method parameters and return types require separate handling.

These boundaries matter: improving hints for most call chains does not mean every generic combination is generated correctly.

Type names and access paths through the CS table

xLua often accesses C# types through CS.UnityEngine.Vector3, while existing annotations may use UnityEngine.Vector3. Treating these as unrelated types produces unhelpful assignment and field-access diagnostics.

The tool generates regular type names by default and offers optional compatibility declarations with a CS. prefix. Both annotation styles should describe the same type, while access through the CS table should also provide member completion.

Both type aliases and table field declarations matter. A name alias alone does not automatically let a language service resolve members along CS.UnityEngine; this was one of the actual issues fixed during the changes.

Choose the annotation style during integration so generated files and handwritten annotations do not develop incompatible naming conventions.

A type alias changes how the editor interprets annotations; it does not create runtime globals. Even with compatibility aliases enabled, xLua must still access the type through CS.UnityEngine.Vector3. Generating annotations does not make UnityEngine.Vector3.zero available at runtime.

Compatibility between C# delegates and Lua functions

The runtime bridge often accepts Lua functions for certain C# delegates, but the language service may not know that conversion rule. For example:

Without more information, it may report that function cannot be assigned to System.Action.

I added a configurable compatibility type list and represent selected delegates as union types at the relevant declaration sites:

This preserves the original C# type while allowing a Lua function. It must also cover method overloads: fixing only ordinary declarations would give the same API different hints depending on whether it entered the overload branch.

The tradeoff is that function is broad and cannot replace precise parameter and return-value checks. The compatibility list should contain only types the runtime can actually convert. For callbacks requiring strict signatures, generating explicit fun(...) declarations would be more appropriate.

Keep static and instance methods distinct

Lua dot and colon calls have different parameter behavior: a colon implicitly passes self. Generating a C# static method as an instance method misaligns the parameter list seen by the editor.

The generator must choose the declaration form using reflection’s IsStatic. I also fixed static functions that still carried instance parameters and cleaned up generic name suffixes, anonymous types, and other names unsuitable for direct exposure.

These details determine whether users trust the hints. Seeing incorrect warnings every day can train people to ignore real problems too.

Make generation suitable for repeated use

Besides type mapping, I added several usability features:

  • Select assembly content by namespace instead of indexing every unrelated type.
  • Generate declarations for globals injected from C# and entry points such as typeof.
  • Split annotation files using a configurable line count to manage large output.
  • Save generation options in an editor window, reducing repeated source-configuration edits.

Whether splitting files improves analysis speed depends on the language service and project size; I did not run a common performance benchmark across editors. The clearer benefit is control over generation scope and output organization.

With Lua Language Server, add the generated directory to workspace.library. Wherever the files are stored, index only the needed declarations and avoid leaving both old and new output that defines the same types twice.

Use a dedicated output directory. This tool cleans old annotations from the destination, so handwritten business scripts must not share that directory.

Integrating it into a project

Clone the repository into the Unity project and wait for editor compilation. Open settings from the top-level LuaType menu, then run generation. Prepare the README’s settings in this order:

Setting How to configure it
Configuration directory Choose a writable directory. The default comes from AppDomain.CurrentDomain.BaseDirectory, which may point into Unity’s installation directory
Annotation output directory Use a dedicated directory ending in the path separator required by the tool; do not store business files there
C# namespaces Add namespaces used by the project, separated by spaces, such as DG FairyGUI
Global variables Use name:type, for example UNITY_EDITOR:boolean DEBUG_LEVEL:number
Lua function compatibility types Enter full type names, such as System.Action FairyGUI.EventCallback0

After generation, verify a real call chain: types under CS, members after a generic singleton, and hints when a delegate parameter receives a Lua function. Regenerate the relevant declarations after adding assemblies, adjusting options, or changing C# APIs.

Language services may differ in annotation compatibility. The README’s support for EmmyLua and SumnekoLua / LuaLS does not imply identical behavior across every version combination. Testing with the project’s actual editor is more reliable than merely checking that files were generated.

From project changes to an upstream merge

This work builds on the original author’s generation logic. I mainly added capabilities and fixes needed by our project. Documenting new options, compatibility boundaries, and usage when submitting upstream makes the changes easier for others to understand than a script that only works in my own project.

PR #2 was merged on March 27, 2025. Tool repository: EmmyLua-Snippet-Generator; original project: EmmyLuaXLuaSnippetGenerator.

Cross-language type hints first reduce everyday guesswork. Passing information already known at runtime to the editor exposes call-chain, parameter, and field problems earlier. Whether an operation is valid still depends on the real runtime rules and tests.
