The Evolution of Unity-Autorun-Tool (2026)

Posted on 2026-08-12 In AI技术 Views:

At the end of 2024, I built a small Unity auto-clicking tool. Every time I entered the game, I had to wait for the scene to load, then click through the connection, login, and entry buttons. This took about half a minute. The actions were simple, but I had to watch the whole process.

The tool later experimented with UI navigation graphs. Version 0.3.4 now uses compiled C# business scripts: an AI reads the host project’s sources and runtime evidence, prepares a flow with explicit starting conditions and assertions, and lets Unity compile and execute it. For repeated self-tests, I run an existing matching script.

The screenshots in this revision show version 0.3.4 running in an isolated Unity demonstration project. They show actual tool behavior and demo configuration, without a production host project’s business data.

From fixed clicks to business scripts

The first version saved a sequence of button operations and waits. It did not shorten the game’s loading time; it removed the need to sit through several repeated clicks. Navigation graphs later helped organize shared entry paths, but a connection between two views was never enough on its own. An entry might depend on player state or asynchronous loading, and different starting states could require different actions to reach the same destination.

Those conditions now live in compiled business scripts. The old navigation graph, graph routing, and manual XML navigation entry points have been retired. Existing host data is not silently converted or deleted; the workflow below uses C# scripts.

Describe one complete self-test

Before writing a script, the AI inspects the host’s sources, Prefabs, and actual runtime state. The tool core provides script contracts, compilation, execution, UI state inspection, and basic interactions. Host-specific view names, business APIs, and operation sequences belong in the host’s business scripts.

New scripts are created under Assets/Editor/AutorunScripts/ in the host project and registered after Unity compilation. A useful script answers four questions:

Part What it must describe
Starting state Required scene, UI, and business state, checked before actions
Actions Verified host APIs and observable conditions to wait for
Dependencies Reused scripts and the parameters explicitly passed to them
Assertions Observable results that establish the requested goal

Every business script declares Preconditions and overrides CheckPreconditions. A wrong start fails before actions; the runner does not guess a different route. Dependency checks detect missing scripts, duplicate IDs, cycles, and undeclared calls.

Reuse requires the same starting conditions, complete actions, and results. Opening inventory from a login screen and opening it from the home screen are different flows, even though they share a destination. They need separate IDs and source files. Generating a new flow never authorizes changing a reused dependency or weakening its starting conditions.

Prepare Play Mode before a cold-start flow

A cold-start root script declares PreparePlayMode=true. The runner enters Play Mode before checking the script’s actual starting scene and UI. The business script also declares and calls the start-play-mode basic dependency to verify preparation. In Edit Mode, the panel presents Start Game & Run for such scripts.

A child’s declaration does not implicitly turn its parent into a cold-start flow. Initial preparation may continue across the Domain Reload caused by entering Play Mode because no business actions have run. An already running C# iterator cannot resume across a reload: unexpected recompilation or a Play Mode change records a failure without replaying completed actions.

Install and connect

The tool requires Unity 2021.3 or newer, Git, and the .NET 8 SDK. In Unity Package Manager, choose Add package from git URL...:

After import and compilation:

  1. Open Window > Auto Run Window.
  2. Expand Connection > MCP Settings & Diagnostics and use Tools > Publish MCP to build the current server.
  3. Under Install, select the project’s .codex or Claude Code .claude directory, then install MCP and Skills. Existing installations may show Update Skills.
  4. Optionally install or update the separate host Agent Rules entry.
  5. Reconnect the AI client. Check that the Bridge is running and inspect the component versions and installation states.

The installation controls come from the current program in the isolated demonstration project. Client installation targets and the host project’s Agent Rules are separate destinations.

Install Skills installs three self-contained packages. Codex uses .agents/skills/ beside the selected .codex directory; Claude Code uses .claude/skills/. The installer validates and stages the batch, rolls back failed replacements, and refuses to overwrite newer installed versions. Claude Desktop supports MCP installation through its configuration directory, but does not load these filesystem Skills there.

When upgrading, publish the server again and update the Skills and Agent Rules as needed. The old unity-autorun Skill is preserved for manual review and removal so customizations are not deleted. Its retired navigation instructions should not remain the current workflow. Existing scripts in Assets/AutorunScripts/Editor/ remain discoverable, while new scripts use Assets/Editor/AutorunScripts/.

Generate, maintain, and run have separate scopes

Skill Responsibility
gen-script Create an authorized new flow, compile it, self-test it, and repair only code created by that task
edit-script Maintain a specified existing business script while preserving its starting state, complete flow, parameters, and goal contract
run-script Inspect and execute an existing script without generating or modifying code

Generation and editing allow up to three repair rounds by default. Editing includes inspecting dependencies and affected callers, waiting for an available idle runner and completed compilation, and regression-testing affected callers from their declared starts. It cannot change reused dependencies or basic scripts to fit the task. A different starting state, flow, or goal needs a separate generated script.

In the editor, select a script under Autorun Scripts and run it. Expand Run Options for string-valued JSON parameters and timeout, Script Details for source and dependencies, and result/history sections for logs and artifacts. Cold-start preparation follows the root declaration; other scripts expose Start game first as an explicit option.

External execution uses get_script_guidance, list_scripts, and get_script for inspection, then start_script and get_script_status for a tracked run and its terminal result. A new self-test uses a fresh runId; only transport retries of the same execution reuse an ID. Compilation success alone does not establish that the requested test passed.

Check existing coverage before creating a self-test

The separate Install Agent Rules / Update Agent Rules action writes instructions into AGENTS.md at the host Unity project’s root. It is intended for agents that read that project’s rules file, and its destination does not depend on the selected client installation directory.

The rule is straightforward: before game or UI actions for self-testing, use list_scripts and get_script(includeSource=true) to inspect the starting state, complete flow, assertions, parameters, and dependencies. Run a valid matching script directly with run-script. If none matches, explain the missing coverage and ask whether the user wants a self-test script created. Do not silently generate one. An explicit creation request already authorizes creation, so it needs no repeated confirmation.

An unavailable MCP connection, Unity, or Bridge blocks discovery; it does not prove that no script exists. A wrong start or invalid dependency is a blocked test, not a reason to quietly substitute another flow.

The managed instructions use the fixed HTML comment markers unity-autorun:agent-instructions:begin and unity-autorun:agent-instructions:end, with a block version. Updates replace only that block and preserve other user rules. Matching content needs no rewrite. Duplicate, missing, or reversed markers, and newer installed versions, prevent an update instead of overwriting the file.

Clicking it invokes the host menu. An omitted or empty path hides the action; invalid detected property types/getters or getter failures produce registration errors, and a menu that cannot execute reports its path.

This configuration window belongs to the demonstration project. The host supplies its contents and save behavior; it is not a built-in business settings screen. Run Options separately controls parameters and timeout for one execution.

Keep evidence and preserve the game state

A click being sent does not prove that a panel opened. get_ui_state and wait_for_ui_state inspect supported structured UI properties, but they do not replace business assertions or establish that animation and layout look correct on every device. Visual evidence still requires inspecting actual screenshots.

The screenshot basic script waits for a complete rendered PNG before recording its artifact. Omitting path saves to Temp/UnityAutorunTool/Screenshots/ in the host project. Before the next default capture, cleanup tries to delete files last written more than 24 hours ago and makes room for the new screenshot, aiming to retain the latest 20 files. Locked files or permissions can prevent complete cleanup; this is not a background timer.

An explicit path does not trigger that cleanup. For long-term evidence, specify a unique project-relative .png path outside the tool’s temporary directory. Files there are not included in the temporary cleanup, and an existing destination fails rather than being overwritten. Old screenshots under AutorunToolData/Screenshots/ are not automatically moved or cleaned.

Success, exceptions, timeouts, and cancellation preserve the current game state and Play Mode. Stopping the game is an explicit action. The runner does not automatically reset the scene, roll back the UI, or replay finished steps. A script’s own exit path releases only resources that invocation owns.

For each self-test, I want the actual compilation result, terminal run state, and goal assertions. If the required start, dependency, or caller regression cannot be checked, the report should say what remains unverified and why. That makes the next run useful without turning missing evidence into a success claim.

The tool still serves the same everyday need: remove repeated operations and leave more time for the issue being investigated. C# scripts now keep the preconditions and expected results with those actions, so the next self-test can reuse the whole flow.
