瀚文微派传记

发表于 2026-09-22 阅读次数：

沈瀚文（ShenHanWen / SHW2002）· 2024—2026 年工作与成长回顾

取材截至 2026 年 9 月 21 日。

沈瀚文在微派的这段经历，可以从一个钓鱼玩法的UI界面讲起。那时需要弄清楚的，是标题应不应该固定、列表如何滚动。后来，同一个人的工作记录里出现了跨端迁移、动画同步、代码生成，以及两名玩家牵手时的关节约束。把这些记录连起来，会看到职责一点点变宽：先把手里的功能做完，再让它经得起完整流程，随后开始为下一次开发、为接手的同事准备可以复用的东西。

2024 年，他在实习与毕业的交接中走进商业游戏开发。计算机和游戏原本就是兴趣，真正进入团队后，兴趣有了具体的承载：正在运营的版本、等待接入的资源、需要一起确认的需求，还有上线之后玩家的反馈。梦幻岛、躲猫猫和《小岛有晴天》各自留下了一段不同的经历，而贯穿其中的，是他逐渐学会把眼前的问题处理得更完整，也把解决办法留下来。

1 2024—2025 年 · 梦幻岛：在成熟项目中建立业务基础

梦幻岛是这段故事的重要起点。项目已经运行着丰富的玩法，也有长期积累的规则，新加入的开发者需要一边做事，一边读懂它。沈瀚文从界面、交互与表现问题入手，逐渐参与钓鱼养成、渔具和载具等成组功能。年度总结里，他特别记下梦幻岛 2.6 在 WePlay 华语服上线：这是他第一次参与研发并跟着走完上线流程，玩家对新玩法的热情让这份工作有了直接的回应。第一次完整交付带来的认识，也具体到了每一个入口：按钮点下去之后，服务器数据、界面和角色状态需要一起接得住。

1.1 钓鱼与载具：从首次上线到状态分工

  • 走完第一次上线： 参与梦幻岛 2.6 钓鱼相关研发，随团队完成华语服上线，开始积累从需求到发布的完整经验。

  • 把角色状态分清楚： 将“已在载具中”与“正在驾驶”拆开，为乘客活动、驾驶和离船建立各自的行为边界。

    • 以 isInVehicle 与 isDriving 分别表达登船和驾驶；进入驾驶必须已经在船上，离船时同步退出驾驶。
    • 镜头与移动模块订阅对应状态变化，使乘客活动和驾驶行为沿各自接口接入。

这段积累有许多很朴素的现场。开发鱼篓界面时，他向 UI 设计同事逐项核对跳转、固定区域、滚动和尺寸规则，双方参照已有界面把交互说清楚，再用实际效果完成确认，得到设计同事的认可。到了载具，同样的辨别逐渐落实为状态接口和模块分工。回看这一阶段，进步就藏在这些具体区分中：先问清一个界面应当怎样使用，再辨明多个玩法怎样共享同一个角色。

1.2 GM 工具重构：让调试命令能够扩展，也容易找到

随着钓鱼和载具持续扩展，团队的调试命令也日益丰富。开发与测试需要按业务快速定位入口，常用操作也适合拥有自己的固定位置。沈瀚文将这些使用需求整理成了新版 GM 工具。它服务于团队每天的调试、复现和验证，把散落在不同功能中的操作组织起来；工具的使用范围也随着协作展开，从开发者延伸到了其他岗位。


梦幻岛 · GM 分类与收藏面板节选

  • 让命令有地方可放： 支持运行时注册分类与命令，业务扩展沿用同一套面板展示和执行流程。

    • 将命令管理从 NLGMPanel 抽到 NLGMTool，把名称、分类与执行函数组织为可注册的数据。
    • 面板统一生成列表，执行结果与错误统一记录，业务模块沿相同方式增加分类和命令。

  • 让常用操作随手可得： 增加跨次启动保留的收藏夹，测试同事确认查找和说明入口更方便，并提出在小岛沿用类似改进。

    • 以命令名称键保存收藏，在下次启动时恢复，并补齐重复收藏拦截与删除后的存储清理。
    • 通过开发组试用和测试用法说明完善交接，收藏与分类进入团队日常调试。

从命令组织、面板接入到收藏保存，沈瀚文把这套工具做成了可以交给同事使用的完整产出，再通过开发组试用、用法说明和反馈继续完善。它也是早期一次清楚的交付练习：自己提出并实现的改进，需要在别人的工作中同样可用。分类与收藏进入日常调试后，开发者增加命令有了共同入口，其他岗位也更容易找到所需操作，工具的价值由此得到实际确认。

1.3 Unity Autorun 初版：把重复进出游戏的步骤交给工具

每次进入游戏，都要经过一段熟悉的准备流程：运行编辑器、等待场景加载，再依次连接服务和进入游戏。这些步骤稳定而重复，也为自动化提供了清楚的入口。Autorun 就从这里开始，让预设接手固定操作，开发者可以利用加载时间安排其他工作，再回到需要验证的内容。这个小工具将一次次日常操作积累成了可复用的流程。

  • 让重复的点击自动完成： 原先进入梦幻岛约需 30 秒等待与手动操作，预设接管了其中的点击流程。

    • 预设记录按钮名称或文字、UI 类型和等待时间，运行后按顺序执行，并支持结束运行前的退出步骤。

  • 从一个工程用到三个： 留存配置覆盖梦幻岛、商城和躲猫猫 3 个项目，包含实际的进入与退出步骤。

    • 按项目保存配置，通过图形界面完成设置；围绕同事使用中的困惑补充教程，空预设时禁用运行入口。

交给同事后，他主动了解大家使用中的困惑，围绕重新拉取工程后的配置步骤更新教程，说明图形界面的使用方式。随着试用交流，工具的配置、说明与操作引导逐步完善，也更便于同事在自己的工程中使用。这个小小的自动入口后来跨过项目边界，在小岛继续演进成导航图；当时留下的配置、文档和试用反馈，都是这条线索的开头。

1.4 梦幻岛钓鱼与载具迁移：走向完整交付

当钓鱼和载具需要从华语服迁移到会玩，工作范围也跟着走出了熟悉的工程。原生客户端能力是否齐全、后台接口是否接通、会玩独有的飞行和其他玩法会不会与登船冲突，都需要重新确认。沈瀚文开始整理调用关系、提测范围和剩余工作，再与团队协调优先级、支援与回归。此前更关注一个功能怎样实现，这次经历让他看到了一个版本怎样在多个岗位之间被接力送到线上。

  • 83 项检查，全部过关： 梦幻岛 2.7 载具部分的当轮冒烟测试共 83 条用例，83 条通过，通过率 100%，由测试同事在项目群确认。

    • 梳理 Unity 调用原生客户端与后台的接口，将道具预览、好友、奖励和图片加载追到具体调用方法与地址。
    • 围绕载具的房间关系与本地坐标，补充飞行、切房、登船和婚礼岛边界的验证重点。

  • 让红点少跑一趟： 纪念册奖励红点的前置刷新路径，对 CollectOverview 的主动请求由 每次 1 次变为 0 次，复用已有数据推送。

    • 确认纪念册数据已有推送，再移除红点判定前的重复请求；赛季点击记录归业务模块管理，通用层维护节点与显示条件。
    • 将获取、兑换、使用与赠送后的刷新纳入验证范围，一并交付优化和检查要求。

迁移中的准备，把接口、玩法与验证联系到了一起。那些在旧环境里积累的业务认识，开始变成他在新环境里主动说明的检查重点；他也在相关版本中积极开展 Code Review，将个人实现带到共同检查的过程中。随后，提测、回归与上线沿着明确的重点推进。这段经历让他从参与功能研发，逐步走向组织自己负责部分的交付，技术判断也成为团队能够执行的安排。

红点优化同样延续了这种完整交付的思路。业务规则与公共能力各有归属，后续使用有了更清楚的接口；请求减少的同时，相关操作后的刷新也获得了明确的验证范围。一次优化因此同时包含实现与检查要求，协作的人能够知道变化发生在哪里、接下来需要关注什么。这些做法逐渐成为他继续维护已有功能时的工作习惯。

  • 让新载具沿共同流程接入： 将资源配置、类型规则和退出流程分别组织，配套编辑器与制作说明。

    • 位置、动作与镜头通过配置适配资源，摩托艇落座等规则由对应载具类型实现。
    • 通过 ExitContext 与 prepareExitVehicle 衔接站起、退出驾驶和离船，将相关流程交付到文档与教学中。

载具的继续扩展，又把这些经验带到了资源制作一侧。编辑器、文档与集中讲解将代码中的约定交到美术手中，模型、动作和镜头的准备能够沿着共同流程推进。到这一阶段结束，留下来的已经包括后续载具能够接入的接口，以及使用者可以照着完成的制作说明。开发工作开始同时关注功能怎样运行，以及其他岗位怎样接着把内容做出来。

1.5 日志治理：从高频输出中找出可消除的开销

完成业务之后，他的目光也开始落到游戏怎样运行。日常调试积累的日志，为观察运行过程提供了线索；进一步按用途和频率梳理这些信息，也成为一项明确的优化方向。他从进入游戏开始采样，按输出次数寻找高频来源，在开发周会上说明保留网络、资源等关键信息的取舍，再推动相关修改优先发布。性能优化在这里有了一个明确的起点：先把正在发生的事情看清楚。

  • 让九百余条重复日志安静下来： 一次从进入梦幻岛持续至帧率稳定后 5 秒的采样中，单一日志输出 900 余条；他记录移除后流畅度明显改善。

    • 按打印次数定位高频来源，保留网络和资源等关键诊断信息，并推动相关修改优先发布。
    • 为红点工具增加默认关闭的调试开关，补充日志标签，继续整理公共加载、网络和角色相关输出。

日志治理也延伸到了日常维护：平时按需要控制输出，排查时保留可以开启的诊断入口，用途与频率都有了明确的安排。梦幻岛时期的几条工作线至此开始汇合，业务实现、工具整理和运行观察共同服务于正在使用的系统。沈瀚文也逐渐习惯在功能完成之后继续看一眼它的运行方式，把可以复用的维护办法留给下一轮开发。

2 2024 年底至 2025 年初 · 躲猫猫：深入实时玩法与多人同步

在梦幻岛持续迭代的同时，沈瀚文也加入了躲猫猫。项目从青鬼的基础上发展而来，已有资源能够复用，玩法规则却需要重新组织。这段经历把他的注意力更集中地带到角色身上：移动、碰撞、镜头和动画要在一次操作中配合，本地玩家按下按钮之后，其他客户端还要看见相应的结果。熟悉旧代码与建立新规则同时发生，对边界的判断也开始进入实时玩法的核心。

2.1 实时玩法：把流程与角色行为接入新规则


躲猫猫 · 反击轨迹开发调试画面

  • 完成主流程与抓捕行为的适配： 参与阶段流程、抓捕者 AI 和反击技能，将移动发现、追击、冻结及真人与 AI 的控制切换接入新规则。

    • AI 记录附近幸存玩家的位置，以移动触发追击，再按时限返回巡逻；冻结、眩晕与真人控制状态统一约束其行为。
    • 保留既有位置同步，把反击的腾空与回落放到模型表现层；本地校验蓄力，远端按释放消息播放，并衔接提前碰撞的收尾。

  • 一次大规模测试的零 Bug 答卷： 据策划同事复盘，最后一次大规模测试发现 0 个 Bug；测试同事的版本同步也确认 1.0 版本测试完成、质量稳定。

这些拆分将玩法规则落实到了角色行为里，也让本地输入、远端表现与控制权交接各有职责。开发时，他需要理解现有框架提供了什么，再为新的规则选择合适的实现位置；联调时，则与服务器核对消息和状态之间的关系。移动、表现和输入的分工由此逐步清楚，既有工程也能够继续承接新的实时玩法。

这些工作由他与导师、另一位客户端开发同事共同推进，阶段测试中的稳定表现也得到了策划和测试的肯定。对于仍在积累完整项目经验的沈瀚文，这是一次很具体的确认：继承的框架有约束，仍然可以通过明确分工把新玩法交出去。后来在小岛区分本地决策与远端表现时，能看见这里留下的经验；项目换了，曾经认真分辨过的问题却继续派上了用场。

2.2 Lua 类型注解工具：从跨语言开发需求走向上游合并

几个项目之间，还有一条工具线索始终没有断。梦幻岛与躲猫猫都使用 Lua 和 C#，跨语言调用时能否得到可靠提示，是写业务时每天都会遇到的问题。沈瀚文最初向导师请教怎样让编辑器识别注解，后来开始修改类型信息生成，继而把实际遇到的需求整理进已有开源生成器。这个过程里，他与工具的关系也在变化：从配置使用者，逐步成为能够修复和扩展它的贡献者。


EmmyLua 注解生成工具 · GitHub 仓库与 README 节选 · 2026-09-22

  • 从项目补丁走进上游： 泛型推断、类型别名、函数兼容等 6 类新增能力随 PR #2 被上游合并，项目内的适配进入原工具的公开版本。

    • 细化常见泛型继承的类型信息，使 Singleton<T>.Instance 等成员获得有效提示；用联合类型表达 C# 委托与 Lua 函数的兼容关系。
    • 支持拆分注解文件、保存生成选项，补齐语言服务目录与兼容配置说明，使工具能在实际工程中反复使用。

改进围绕项目里真实出现的跨语言调用展开，配置说明也随着工程使用逐步补齐。仓库先分享给同事试用，再将改动提交上游，让代码生成、编辑器配置与公开维护连接起来。对这段经历而言，合并记录是清楚的成果，而更长久的变化是：一次为当前工程解决的问题，经过整理，已经能够被其他开发者继续使用，也让他积累了参与开源协作的经验。

3 2025 年下半年至 2026 年 · 小岛有晴天：从角色操控走向同步架构

来到《小岛有晴天》，沈瀚文迎来了职责上的一次明显变化。年度复盘里，他将这里记作第一次从零开始完整负责一个游戏模块的经历：在项目既有框架上推进 3C 的方案、实现与持续迭代，逐步把角色、相机和操控组织成可供后续玩法使用的基础。需求有时以参考视频开始，他便分析操作关系，做出试玩版与策划对齐，再继续安排同步、配置和资源接入。此前项目中积累的经验，在这里形成了由他持续负责的一段完整工作。

3.1 首次完整负责 3C：从方案探索到持续交付

  • 承担核心模块的完整周期： 从参考内容分析、试玩验证到方案实现与后续迭代，持续负责小岛 3C 的建设。

    • 先形成可体验的版本，与策划核对操作和表现，再把确认后的规则落实到角色控制与动画方案中。
