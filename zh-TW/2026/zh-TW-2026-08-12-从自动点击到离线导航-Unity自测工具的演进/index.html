自動測試工具Unity-Autorun-Tool的演進(2026)

發表於 2026-08-12 分類於 AI技術 閱讀次數：

2024 年底，我做了一個很小的 Unity 自動點擊工具。原因也很簡單：每次進遊戲都要等待場景加載，再依次點幾個連接、登錄和進入遊戲的按鈕。這段流程大約持續半分鐘，操作不復雜，卻要一直盯著。

工具後來嘗試過 UI 導航圖，現在的 0.3.4 則把流程交給可編譯的 C# 業務腳本：AI 根據項目源碼和運行時證據準備代碼，Unity 編譯並執行，腳本自己說明從哪裡開始、做哪些動作，以及用什麼結果判斷成功。日常重複自測時，我直接運行已有腳本。

新版在隔離 Unity 演示工程中的實際界面，展示工具操作，不含宿主項目的業務數據；點擊圖片可打開倉庫。本文使用方式按 0.3.4 更新。

從點擊預設到業務腳本

第一版只保存順序操作：找到按鈕、必要時核對文字、等待一段時間，再執行下一步。它沒有縮短遊戲加載時間，只是讓我不必守著完成那幾次固定點擊。

界面多起來以後，我用過導航圖來整理界面、控件和跳轉關係。共享的登錄流程可以複用，但僅有“從主界面能打開背包”的關係還不夠：入口可能受等級限制，可能要等待異步數據，同一個終點也可能有不同起點和業務流程。這些條件最終仍然需要落實到項目代碼裡。

現在我把這部分邏輯寫進業務腳本，由 Unity 編譯。舊導航圖、圖路由和手動 XML 導航入口已經移除，下文的使用方式都以 C# 腳本為準。舊數據不會被靜默轉換或刪除，從舊版升級時需要重新檢查自己的流程。

一個腳本要說明完整的一次自測

AI 生成代碼之前，要先查看宿主項目的源碼、Prefab 和實際運行狀態。工具核心只提供腳本契約、編譯與運行、UI 狀態和基礎交互，具體界面名稱、業務 API 與操作順序留在宿主的業務腳本里。

新腳本放在宿主項目的 Assets/Editor/AutorunScripts/，由 Unity 編譯後註冊。對我來說，腳本至少要回答四個問題：

內容 要說明什麼
起點 需要什麼場景、界面和業務狀態，動作前如何檢查
動作 調用什麼已核實的宿主 API，等待什麼狀態
依賴 複用了哪些腳本，各自需要什麼參數
斷言 最終觀察到什麼，才能說明這次目標完成

每個業務腳本聲明 Preconditions，並實現 CheckPreconditions。起點不符就直接失敗，不在執行時另猜一條路線。調用依賴也必須提前聲明；缺失依賴、重複 ID、循環和未聲明調用都會被檢查。

複用的單位是起點、動作和結果都一致的完整業務片段。同樣是打開背包，從登錄頁開始和從主界面開始就是兩條不同流程，應使用獨立 ID 和文件；不能為了複用，臨時修改原腳本或降低起點要求。

冷啟動先準備 Play Mode

需要從未運行狀態開始的根腳本聲明 PreparePlayMode=true。運行器先準備 Play Mode，再檢查實際場景和 UI 起點；腳本同時聲明並調用 start-play-mode 基礎腳本，複用準備結果的校驗。停止狀態下，面板會直接顯示 Start Game & Run。

子腳本有這個聲明，不會隱式把整個父流程變成冷啟動流程。已經開始執行的 C# 迭代器也不能跨 Domain Reload 恢復；運行中意外重編譯或切換 Play Mode，會留下失敗結果，不自動重放前面已經完成的操作。

接入與運行

導入並編譯完成後，打開 Window > Auto Run Window：

  1. 展開 Connection > MCP Settings & Diagnostics，點擊 Publish MCP。
  2. 在 Install 中選擇項目的 .codex 或 Claude Code 的 .claude 目錄，分別安裝 Install MCP 和 Install Skills。
  3. 重新連接 AI 客戶端，核對 Bridge 的 Running 狀態和對應 MCP 進程，再檢查 Versions 中各組件的狀態。

隔離演示工程中的安裝界面。客戶端 MCP、三個 Skill 和宿主 Agent Rules 分別展示狀態，版本號不要求完全一致。

三個 Skill 分工如下：

Skill 用途
gen-script 創建新業務流程，編譯、自測，並修正本次生成的代碼
edit-script 維護用戶指定的已有業務腳本，保持原有起點、流程與目標契約
run-script 查找並運行已有腳本，等待終態並核對斷言，不生成或修改代碼

已有腳本需要修復時，edit-script 先讀取指定腳本、依賴和反向調用者，確認沒有運行中的任務、Unity 也未在編譯，才開始修改。修改後重新編譯，使用新的 runId 自測，並從各自起點回歸受影響的調用者。若需求改變了起點、流程或目標，應交給 gen-script 新建獨立腳本，而不是把舊腳本改成另一條流程。

平時我在 Autorun Scripts 中搜索並選擇腳本，點擊 Run Script 或 Start Game & Run。默認界面保留運行入口和簡短結果，需要時再展開 Script Details、Run Options、Result Details 與 Recent Runs 查看起點、依賴、參數、日誌和產物。外部調用則通過 start_script 啟動，再用 get_script_status 等待終態；同一次請求的傳輸重試沿用 runId，新的自測另用新 ID。

Install Skills 會把三個自包含安裝包作為整批處理：先驗證與暫存，再備份和替換，失敗時回滾；已安裝版本更高就拒絕覆蓋。Codex 的目標是所選 .codex 同級的 .agents/skills/，Claude Code 使用 .claude/skills/。舊 unity-autorun Skill 會保留，檢查過用戶定製後再手動卸載。Claude Desktop 在這裡僅支持安裝 MCP，不通過其配置目錄加載這三個文件系統 Skill。

自測之前，先找已有腳本

我不希望 Agent 每次需要操作遊戲時，都重新生成一份相近的代碼。因此，Agent Rules 是獨立於 MCP 和 Skill 安裝的入口：明確點擊 Install Agent Rules 或 Update Agent Rules 後，才會把規則寫進當前宿主 Unity 項目根目錄的 AGENTS.md，不跟隨客戶端目錄變化。

規則要求 Agent 在遊戲或 UI 操作自測前，先用 list_scripts 和 get_script(includeSource=true) 核對已有腳本的起點、完整流程、斷言、參數與依賴。找到匹配且有效的腳本，就交給 run-script 直接執行；沒找到時，說明缺少什麼覆蓋，再詢問是否需要創建自測腳本，不能靜默新建。用戶已經明確授權創建時，不重複確認。

MCP、Unity 或 Bridge 不可用屬於檢查阻塞，不能據此聲稱“沒有腳本”；起點不匹配也不能隨手拼一條替代流程。

寫入內容由 unity-autorun:agent-instructions:begin / end HTML 註釋標記識別，並記錄區塊版本。更新只替換管理區塊，保留其他用戶規則；內容一致時無需重寫。標記重複、單側缺失、順序錯誤或已安裝版本更高時會報告問題，避免覆蓋用戶文件。

從腳本直接打開宿主配置

有些流程運行前要先核對項目配置。我給腳本面板加了“打開配置界面”入口，沿用宿主已有的編輯器菜單，不在工具裡再做一份業務配置 UI。

業務腳本可以提供帶公開 getter 的 public static string ConfigurationMenuPath 屬性，值填寫宿主實際存在的 [MenuItem] 路徑。編譯並刷新後，選中這個腳本即可打開對應菜單；未聲明或返回空值時不顯示入口。屬性不合規或菜單無法執行時會顯示錯誤。Run Options 仍用於本次運行的參數和超時，兩者用途不同。

這裡打開的是隔離演示工程提供的配置窗口。具體配置內容與保存方式由宿主實現，不是工具內置的業務界面。

留下結果，也留下現場

發送過點擊不代表界面已經打開，腳本正常結束也不代表業務目標通過。get_ui_state 和 wait_for_ui_state 能讀取、等待支持範圍內的結構化 UI 值；它們不能替代宿主業務斷言，也不能證明動效和不同設備的視覺表現。需要視覺證據時，仍然要檢查實際截圖。

默認運行截圖放在宿主的 Temp/UnityAutorunTool/Screenshots/。清理發生在下一次默認截圖之前：盡力刪除超過 24 小時的文件，併為新截圖騰出位置，使總量維持在最多 20 份；文件被佔用等情況可能使清理不完整，它也不是後臺定時任務。顯式指定 path 不觸發這項自動清理；需要長期留存的證據，應指定宿主項目內、臨時目錄之外的 .png 路徑。

正常完成、異常、超時和取消都會保留當時的遊戲現場與 Play Mode。停止遊戲必須是明確動作，不在失敗後自動重置或回退。腳本自己的事件訂閱、臨時對象等資源由自己的退出路徑清理。

對一次自測，我需要看到實際編譯結果、運行終態和目標斷言。編譯通過不能替代自測通過；缺少正確起點、依賴或調用者回歸條件時，就保留證據，寫清楚哪些部分沒有驗證。

這個工具仍然服務於最初的需求：少重複幾次固定操作，把時間留給正在檢查的問題。現在我更看重的是，把這次操作的前提和結果一起留下，讓下一次能可靠地複用。

項目地址：Unity-Autorun-MCP。後續安裝方式和接口以對應版本的 README 為準。
