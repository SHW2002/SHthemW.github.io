瀚文微派傳記

發表於 2026-09-22 分類於 遊戲開發 閱讀次數：

沈瀚文（ShenHanWen / SHW2002）· 2024—2026 年工作與成長回顧

沈瀚文在微派的這段經歷，可以從一個釣魚玩法的UI界面講起。那時關心的是標題固定、列表滾動，後來工作記錄裡逐漸出現了跨端遷移、動畫同步和代碼生成。把這些記錄連起來，會看到職責一點點變寬：先把手裡的功能做完，再讓它經得起完整流程，隨後開始為下一次開發、為接手的同事準備可以複用的東西。

2024 年，他在實習與畢業的交接中走進商業遊戲開發。計算機和遊戲原本就是興趣，真正進入團隊後，興趣有了具體的承載：正在運營的版本、等待接入的資源、需要一起確認的需求，還有上線之後玩家的反饋。夢幻島、躲貓貓和《小島有晴天》各自留下了一段不同的經歷，而貫穿其中的，是他逐漸學會把眼前的問題處理得更完整，也把解決辦法留下來。

1 2024—2025 年 · 夢幻島：在成熟項目中建立業務基礎

夢幻島是這段故事的重要起點。項目已經運行著豐富的玩法，也有長期積累的規則，新加入的開發者需要一邊做事，一邊讀懂它。沈瀚文從界面、交互與表現問題入手，逐漸參與釣魚養成、漁具和載具等成組功能。年度總結裡，他特別記下夢幻島 2.6 在 WePlay 華語服上線：這是他第一次參與研發並跟著走完上線流程，玩家對新玩法的熱情讓這份工作有了直接的回應。第一次完整交付帶來的認識，也具體到了每一個入口：按鈕點下去之後，服務器數據、界面和角色狀態需要一起接得住。

1.1 釣魚與載具：從首次上線到狀態分工

  • 走完第一次上線： 參與夢幻島 2.6 釣魚相關研發，隨團隊完成華語服上線，開始積累從需求到發佈的完整經驗。

  • 把角色狀態分清楚： 將“已在載具中”與“正在駕駛”拆開，為乘客活動、駕駛和離船建立各自的行為邊界。

    • 以 isInVehicle 與 isDriving 分別表達登船和駕駛；進入駕駛必須已經在船上，離船時同步退出駕駛。
    • 鏡頭與移動模塊訂閱對應狀態變化，使乘客活動和駕駛行為沿各自接口接入。

這段積累有許多很樸素的現場。開發魚簍界面時，他向 UI 設計同事逐項核對跳轉、固定區域、滾動和尺寸規則，雙方參照已有界面把交互說清楚，再用實際效果完成確認，得到設計同事的認可。到了載具，同樣的辨別逐漸落實為狀態接口和模塊分工。回看這一階段，進步就藏在這些具體區分中：先問清一個界面應當怎樣使用，再辨明多個玩法怎樣共享同一個角色。

1.2 GM 工具重構：讓調試命令能夠擴展，也容易找到

隨著釣魚和載具持續擴展，團隊的調試命令也日益豐富。開發與測試需要按業務快速定位入口，常用操作也適合擁有自己的固定位置。沈瀚文將這些使用需求整理成了新版 GM 工具。它服務於團隊每天的調試、復現和驗證，把散落在不同功能中的操作組織起來；工具的使用範圍也隨著協作展開，從開發者延伸到了其他崗位。


夢幻島 · GM 分類與收藏面板節選

  • 讓命令有地方可放： 支持運行時註冊分類與命令，業務擴展沿用同一套面板展示和執行流程。

    • 將命令管理從 NLGMPanel 抽到 NLGMTool，把名稱、分類與執行函數組織為可註冊的數據。
    • 面板統一生成列表，執行結果與錯誤統一記錄，業務模塊沿相同方式增加分類和命令。

  • 讓常用操作隨手可得： 增加跨次啟動保留的收藏夾，測試同事確認查找和說明入口更方便，並提出在小島沿用類似改進。

    • 以命令名稱鍵保存收藏，在下次啟動時恢復，並補齊重複收藏攔截與刪除後的存儲清理。
    • 通過開發組試用和測試用法說明完善交接，收藏與分類進入團隊日常調試。

從命令組織、面板接入到收藏保存，沈瀚文把這套工具做成了可以交給同事使用的完整產出，再通過開發組試用、用法說明和反饋繼續完善。它也是早期一次清楚的交付練習：自己提出並實現的改進，需要在別人的工作中同樣可用。分類與收藏進入日常調試後，開發者增加命令有了共同入口，其他崗位也更容易找到所需操作，工具的價值由此得到實際確認。

1.3 Unity Autorun 初版：把重複進出遊戲的步驟交給工具

每次進入遊戲，都要經過一段熟悉的準備流程：運行編輯器、等待場景加載，再依次連接服務和進入遊戲。這些步驟穩定而重複，也為自動化提供了清楚的入口。Autorun 就從這裡開始，讓預設接手固定操作，開發者可以利用加載時間安排其他工作，再回到需要驗證的內容。這個小工具將一次次日常操作積累成了可複用的流程。

  • 讓重複的點擊自動完成： 原先進入夢幻島約需 30 秒等待與手動操作，預設接管了其中的點擊流程。

    • 預設記錄按鈕名稱或文字、UI 類型和等待時間，運行後按順序執行，並支持結束運行前的退出步驟。

  • 從一個工程用到三個： 留存配置覆蓋夢幻島、商城和躲貓貓 3 個項目，包含實際的進入與退出步驟。

    • 按項目保存配置，通過圖形界面完成設置；圍繞同事使用中的困惑補充教程，空預設時禁用運行入口。

交給同事後，他主動瞭解大家使用中的困惑，圍繞重新拉取工程後的配置步驟更新教程，說明圖形界面的使用方式。隨著試用交流，工具的配置、說明與操作引導逐步完善，也更便於同事在自己的工程中使用。這個小小的自動入口後來跨過項目邊界，在小島繼續演進成導航圖；當時留下的配置、文檔和試用反饋，都是這條線索的開頭。

1.4 夢幻島釣魚與載具遷移：走向完整交付

當釣魚和載具需要從華語服遷移到會玩，工作範圍也跟著走出了熟悉的工程。原生客戶端能力是否齊全、後臺接口是否接通、會玩獨有的飛行和其他玩法會不會與登船衝突，都需要重新確認。沈瀚文開始整理調用關係、提測範圍和剩餘工作，再與團隊協調優先級、支援與迴歸。此前更關注一個功能怎樣實現，這次經歷讓他看到了一個版本怎樣在多個崗位之間被接力送到線上。

  • 83 項檢查，全部過關： 夢幻島 2.7 載具部分的當輪冒煙測試共 83 條用例，83 條通過，通過率 100%，由測試同事在項目群確認。

    • 梳理 Unity 調用原生客戶端與後臺的接口，將道具預覽、好友、獎勵和圖片加載追到具體調用方法與地址。
    • 圍繞載具的房間關係與本地座標，補充飛行、切房、登船和婚禮島邊界的驗證重點。

  • 讓紅點少跑一趟： 紀念冊獎勵紅點的前置刷新路徑，對 CollectOverview 的主動請求由 每次 1 次變為 0 次，複用已有數據推送。

    • 確認紀念冊數據已有推送，再移除紅點判定前的重複請求；賽季點擊記錄歸業務模塊管理，通用層維護節點與顯示條件。
    • 將獲取、兌換、使用與贈送後的刷新納入驗證範圍，一併交付優化和檢查要求。

遷移中的準備，把接口、玩法與驗證聯繫到了一起。那些在舊環境裡積累的業務認識，開始變成他在新環境裡主動說明的檢查重點；他也在相關版本中積極開展 Code Review，將個人實現帶到共同檢查的過程中。隨後，提測、迴歸與上線沿著明確的重點推進。這段經歷讓他從參與功能研發，逐步走向組織自己負責部分的交付，技術判斷也成為團隊能夠執行的安排。

紅點優化同樣延續了這種完整交付的思路。業務規則與公共能力各有歸屬，後續使用有了更清楚的接口；請求減少的同時，相關操作後的刷新也獲得了明確的驗證範圍。一次優化因此同時包含實現與檢查要求，協作的人能夠知道變化發生在哪裡、接下來需要關注什麼。這些做法逐漸成為他繼續維護已有功能時的工作習慣。

  • 讓新載具沿共同流程接入： 將資源配置、類型規則和退出流程分別組織，配套編輯器與製作說明。

    • 位置、動作與鏡頭通過配置適配資源，摩托艇落座等規則由對應載具類型實現。
    • 通過 ExitContext 與 prepareExitVehicle 銜接站起、退出駕駛和離船，將相關流程交付到文檔與教學中。

載具的繼續擴展，又把這些經驗帶到了資源製作一側。編輯器、文檔與集中講解將代碼中的約定交到美術手中，模型、動作和鏡頭的準備能夠沿著共同流程推進。到這一階段結束，留下來的已經包括後續載具能夠接入的接口，以及使用者可以照著完成的製作說明。開發工作開始同時關注功能怎樣運行，以及其他崗位怎樣接著把內容做出來。

1.5 日誌治理：從高頻輸出中找出可消除的開銷

完成業務之後，他的目光也開始落到遊戲怎樣運行。日常調試積累的日誌，為觀察運行過程提供了線索；進一步按用途和頻率梳理這些信息，也成為一項明確的優化方向。他從進入遊戲開始採樣，按輸出次數尋找高頻來源，在開發週會上說明保留網絡、資源等關鍵信息的取捨，再推動相關修改優先發布。性能優化在這裡有了一個明確的起點：先把正在發生的事情看清楚。

  • 讓九百餘條重複日誌安靜下來： 一次從進入夢幻島持續至幀率穩定後 5 秒的採樣中，單一日誌輸出 900 餘條；他記錄移除後流暢度明顯改善。

    • 按打印次數定位高頻來源，保留網絡和資源等關鍵診斷信息，並推動相關修改優先發布。
    • 為紅點工具增加默認關閉的調試開關，補充日誌標籤，繼續整理公共加載、網絡和角色相關輸出。

日誌治理也延伸到了日常維護：平時按需要控制輸出，排查時保留可以開啟的診斷入口，用途與頻率都有了明確的安排。夢幻島時期的幾條工作線至此開始匯合，業務實現、工具整理和運行觀察共同服務於正在使用的系統。沈瀚文也逐漸習慣在功能完成之後繼續看一眼它的運行方式，把可以複用的維護辦法留給下一輪開發。

2 2024 年底至 2025 年初 · 躲貓貓：深入實時玩法與多人同步

在夢幻島持續迭代的同時，沈瀚文也加入了躲貓貓。項目從青鬼的基礎上發展而來，已有資源能夠複用，玩法規則卻需要重新組織。這段經歷把他的注意力更集中地帶到角色身上：移動、碰撞、鏡頭和動畫要在一次操作中配合，本地玩家按下按鈕之後，其他客戶端還要看見相應的結果。熟悉舊代碼與建立新規則同時發生，對邊界的判斷也開始進入實時玩法的核心。

2.1 實時玩法：把流程與角色行為接入新規則


躲貓貓 · 反擊軌跡開發調試畫面

  • 完成主流程與抓捕行為的適配： 參與階段流程、抓捕者 AI 和反擊技能，將移動發現、追擊、凍結及真人與 AI 的控制切換接入新規則。

    • AI 記錄附近倖存玩家的位置，以移動觸發追擊，再按時限返回巡邏；凍結、眩暈與真人控制狀態統一約束其行為。
    • 保留既有位置同步，把反擊的騰空與回落放到模型表現層；本地校驗蓄力，遠端按釋放消息播放，並銜接提前碰撞的收尾。

  • 一次大規模測試的零 Bug 答卷： 據策劃同事復盤，最後一次大規模測試發現 0 個 Bug；測試同事的版本同步也確認 1.0 版本測試完成、質量穩定。

這些拆分將玩法規則落實到了角色行為裡，也讓本地輸入、遠端表現與控制權交接各有職責。開發時，他需要理解現有框架提供了什麼，再為新的規則選擇合適的實現位置；聯調時，則與服務器核對消息和狀態之間的關係。移動、表現和輸入的分工由此逐步清楚，既有工程也能夠繼續承接新的實時玩法。

這些工作由他與導師、另一位客戶端開發同事共同推進，階段測試中的穩定表現也得到了策劃和測試的肯定。對於仍在積累完整項目經驗的沈瀚文，這是一次很具體的確認：繼承的框架有約束，仍然可以通過明確分工把新玩法交出去。後來在小島區分本地決策與遠端表現時，能看見這裡留下的經驗；項目換了，曾經認真分辨過的問題卻繼續派上了用場。

2.2 Lua 類型註解工具：從跨語言開發需求走向上游合併

幾個項目之間，還有一條工具線索始終沒有斷。夢幻島與躲貓貓都使用 Lua 和 C#，跨語言調用時能否得到可靠提示，是寫業務時每天都會遇到的問題。沈瀚文最初嚮導師請教怎樣讓編輯器識別註解，後來開始修改類型信息生成，繼而把實際遇到的需求整理進已有開源生成器。這個過程裡，他與工具的關係也在變化：從配置使用者，逐步成為能夠修復和擴展它的貢獻者。


EmmyLua 註解生成工具 · GitHub 倉庫與 README 節選 · 2026-09-22

  • 從項目補丁走進上游： 泛型推斷、類型別名、函數兼容等 6 類新增能力隨 PR #2 被上游合併，項目內的適配進入原工具的公開版本。

    • 細化常見泛型繼承的類型信息，使 Singleton<T>.Instance 等成員獲得有效提示；用聯合類型表達 C# 委託與 Lua 函數的兼容關係。

  • 平滑留在本地，發包按需減頻： 牽手位姿的週期發送配置由 30 毫秒改為 100 毫秒，名義頻率從約 33.3 Hz 降至 10 Hz，降低 70%；手部 IK 目標由 30 毫秒改為 200 毫秒，名義頻率降至 5 Hz，降低 85%。

    • 雙方位姿進入帶採樣時間的共同快照，被牽方與旁觀者沿同一時間軸插值；短時缺包限時外推，傳送或長時間中斷則重建基準。
    • 由發起方每幀統一計算和平滑動畫速度，使用不同起停閾值，並獨立配置位姿、動畫與 IK 的發送間隔。
    • 非本地服自測記錄了平滑體感改善，對應直線移動卡頓事項隨後關閉。

這個階段的成果，能夠同時從體驗反饋、具體實現和發送配置中找到依據。位置、關節與動畫參數分別平滑，網絡節奏也可以獨立調整，幾種機制共同服務於連續的雙人表現。沈瀚文處理問題的方法由此從單點修正，走向對計算、傳輸和播放之間關係的整體安排。此前在角色系統中積累的經驗，也在這項複雜交互裡形成了更完整的配合。

尾記：把一次交付變成下一次的起點

回看這幾段經歷，沈瀚文的成長有著清楚的脈絡。夢幻島讓他熟悉商業遊戲的開發與協作，在釣魚、載具和工具建設中積累完整交付的經驗；躲貓貓把他的注意力帶向實時玩法與多人同步；到了小島，這些經驗匯入由他持續負責的 3C 模塊。從理解已有系統，到選擇技術方案，再到承擔實現、自測與後續迭代，他逐漸能夠把一個模塊的工作完整接住，也能為下一批內容留下可繼續使用的基礎。

交付質量與團隊協作，讓這些技術積累有了更具體的回應。階段測試中的穩定表現、同事對工具的認可、代碼在後續業務中的複用，以及開源改進被上游接納，都留下了可以回看的成果。與此同時，他開始把製作經驗寫成文檔，把命名和校驗落實到生成規則，參與代碼審查與新人支持。自己掌握的方法因此能夠被更多人理解和使用，個人負責的範圍也逐步延伸到共同交付的過程。
