Unity Skinned Bounds and Adaptive Display Model Scaling

Posted on 2026-06-18 In 游戏开发 Views:

For collection and leaderboard displays, characters and held models must fit a fixed space. Clothing and item combinations are too numerous to tune individually, so I limited their overall size using bounds.

Some characters then shrank into tiny dots. The scaling formula looked correct; the real problem was the “model size” supplied to it.

Establish what to measure

The display needs the space occupied by participating models in a specified pose. This need not match the mesh asset’s original size or imported bounds covering several animations.

Unity provides several easily confused values:

Data Coordinate space Display considerations
Mesh.bounds Mesh-local Original skinned vertices do not represent the current animated pose
SkinnedMeshRenderer.localBounds Renderer-local May be a conservative animation envelope rather than a tight fit
Renderer.bounds World-space AABB Affected by rotation, skinning updates, and culling
A mesh from BakeMesh Renderer-local A snapshot of the current skinned pose; transformations still need care

During the first investigation, the drawn box was much larger than the character. The size limiter treated that inflated box as the real model and kept shrinking the character.

Cropped from the original Scene view to retain only the character-to-bounds size relationship.

Moving the camera farther away does not fix measurement. It changes projection, while an incorrect measured size still makes the limiter shrink the model improperly.

The first attempt: BakeMesh

SkinnedMeshRenderer.BakeMesh produces a snapshot of the current skinned mesh. When static bounds are too conservative, comparing the baked mesh with Renderer bounds helps determine whether the discrepancy comes from an asset envelope or the current pose.

Do not simply treat mesh.bounds.size as a world size after baking. In a general hierarchy, transform the local box’s eight corners into a common coordinate space and combine them into a new AABB.

Two common mistakes are:

  • Multiplying local size by lossyScale and ignoring rotation’s effect on the world AABB.
  • Baking with scale included, then applying the same scale again in a later matrix transformation.

Our project has an additional complication: clothing bones are rebound to the character skeleton, so the Renderer node’s scale and actual skinning do not always follow a simple hierarchy relationship. Applying “local box times Transform” can collapse the result to a point or inflate it unexpectedly.

I therefore did not settle on BakeMesh as the final solution and continued examining our skinning updates. Baking provides information, but cannot replace confirming the skeleton and coordinate spaces.

Correct size also requires correct timing

The second issue occurred during loading. The character, clothing, and held item become ready separately; resource changes may also cause the Animator to Rebind. Measuring immediately can capture the bind pose or unstable bones.

The same assets working sometimes and failing at other times is typical of this timing problem. I changed the sequence to:

  1. Wait for the character, clothing, and held item to be ready.
  2. Finish refreshing the animation controller and skeleton.
  3. Pass the rebind frame and evaluate the display pose in a subsequent update phase.
  4. Confirm skinning has updated, then collect participating Renderers.
  5. Combine bounds and calculate uniform scaling.

For this dedicated display character, I evaluate a known Idle pose before measurement:

This changes the current pose, so it suits a display character during initialization, rather than resetting a character currently being played. Measuring Idle only establishes its size in that pose; it cannot guarantee later waving, jumping, or every other animation fits the same space.

Offscreen updating is another measurement condition

Display models often finish loading outside the camera view. Even when resources exist, offscreen culling may prevent expected animation or skinning updates.

I enabled updateWhenOffscreen on the relevant SkinnedMeshRenderers and combined it with a known Animator pose and later-frame measurement to obtain usable world-space bounds in our project. This also avoided reconstructing world bounds for unusual skinning hierarchies myself.

This does not mean one switch instantly makes every model’s Bounds accurate. Check whether the project overrides Bounds, whether the skeleton has stabilized, and whether this frame’s animation and skinning evaluation has actually finished.

Continuous offscreen updates cost time. Our limited number of display objects makes that tradeoff acceptable. For many characters, restrict which objects update and for how long, then check results after restoring culling.

Combine only objects actually displayed

A character hierarchy may contain hidden old parts, inactive held items, and particle effects as well as visible clothing. These can inflate bounds.

Filter before collecting:

Use world-space data for the remaining objects and combine it with Bounds.Encapsulate. Initialize from the first valid Renderer, not a zero-sized box at the world origin; otherwise a model away from the origin includes irrelevant space.

I also record which Renderer supplies each axis’s minimum and maximum. That identifies whether clothing inflated X or a bone-associated part stretched Y, rather than exposing only one huge final number.

Scale uniformly using the tightest axis

Let measuredSize be the current size and targetSize the allowed display space. To shrink oversized models without enlarging small ones:

Reject empty collections, zero dimensions, and non-finite values first. Measure under a consistent initial scale; do not repeatedly multiply a model that has already been scaled.

Uniform scaling preserves the character-to-item proportions, but flat or wide items often hit horizontal limits first. Adjust the display space or configure target boxes by resource category instead of loosening every display’s limits for one model.

This solves a three-dimensional size constraint. Keeping the whole model visible in a perspective-camera UI window also depends on view angle, FOV, and screen projection. A world AABB does not guarantee that the image will never be cropped.

The most useful diagnostic information

Starting with abnormal bounds in mid-June, I traced skeleton rebinding, offscreen updates, and measurement timing. For similar problems, first record the current pose, participating Renderers, each axis’s extreme-value sources, and the loading phase when measurement occurs.

Adjusting only the final scale can temporarily hide the fault. Once the measured object, frame, and coordinate space are correct, the fitting formula is straightforward.
