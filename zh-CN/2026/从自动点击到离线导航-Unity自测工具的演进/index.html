自动测试工具Unity-Autorun-Tool的演进(2026)

发表于 2026-08-12 分类于 开发工具 阅读次数：

2024 年底，我做了一个很小的 Unity 自动点击工具。原因也很简单：每次进游戏都要等待场景加载，再依次点几个连接、登录和进入游戏的按钮。这段流程大约持续半分钟，操作不复杂，却要一直盯着。

最初我只想把这些点击交给预设。后来要自测的界面越来越多，工具又逐步增加了 UI 导航图、编辑器入口和外部调用接口。现在可以先准备好界面之间的路径，日常调试时直接选择目标，让程序完成中间的导航。

第一版只处理固定步骤

初版在 2024 年 11 月完成基本功能，随后补充退出前的动作和使用说明。一个预设保存一组顺序操作，每项主要包含：

字段 作用
按钮名称 定位要操作的对象
按钮文字 必要时辅助区分同名按钮
等待时间 等待场景或界面准备完成
UI 框架 选择 UGUI 或 FairyGUI 的处理方式

运行工具之后，进入 Play Mode，再按顺序执行配置。后来增加的 Stop 动作则在停止运行之前执行，例如先退出当前房间，再结束调试。

这版工具没有缩短游戏自身的加载时间。它省掉的是等待期间必须由人完成的几次操作，让我能够在加载时去做别的事情。

同一套机制后来用于几个不同工程。项目之间的登录流程虽然不一样，但只要调整预设，就不必为每个工程再写一套编辑器按钮。

从操作序列到界面关系

顺序预设适合固定入口，界面变多之后却会暴露两个问题。

第一，多个目标会共享前半段流程。例如打开背包与打开设置都要先进入主界面，为每个目标复制一份完整序列，会让登录流程的改动传播到很多预设。

第二，执行起点不一定相同。有时还未进入 Play Mode，有时已经在主界面，有时正停在一个弹窗里。只有一串按钮名称，很难表达这些差异。

因此我开始用导航图描述 UI，把信息拆成界面、控件、跳转和路由：

概念 记录的内容
View 一个可以识别的界面或面板
Control 导航需要操作的按钮等控件
Transition 从某个界面到另一个界面的操作关系
Route 一条可复用的导航路径

简化示意，界面名称与具体项目无关。共享的登录流程只需要维护一次。

图里的一条边也不能只写“主界面可以打开背包”。还要知道通过哪个控件执行、到达后用什么条件确认，以及在当前环境下是否具备执行前提。

静态代码里存在一次打开界面的调用，说明存在可达关系，但不代表自动化工具马上就能走通。例如入口可能受等级条件限制，或者必须先完成一次异步操作。这些缺口需要保留下来，不能当作已经验证的路径。

AI 参与准备，日常导航由程序执行

项目里有很多 UI 调用，手工整理完整导航图本身也有成本。我让 AI 辅助分析源码中的界面关系，把候选整理成导航数据，再根据工具能够识别和执行的条件进行检查。

这里把两类工作分开：

  • 准备阶段理解代码与界面语义，生成或修订导航图。
  • 执行阶段读取已准备的图，运行确定的步骤，等待结果并报告状态。

路径已经具备后，点击编辑器按钮或通过命令行运行，不需要再让模型为每一步重新做决定。这里说的“离线导航”是指执行过程不依赖 AI 推理，游戏本身仍然可能需要连接服务器。

这也给维护划出了范围：界面结构或跳转逻辑改动时更新相应数据；没有变化的路径继续复用。导航图是一份需要随项目维护的工具数据，并不是生成一次就永远有效。

点击完成与导航完成是两件事

早期顺序预设主要依赖等待时间，但固定延迟有明显局限。机器负载、资源缓存和网络响应变化后，同样等两秒可能太短，也可能白等很久。

导航执行更适合围绕状态组织：

发送点击只代表执行过操作，不代表目标面板已经打开。反过来，某个 GameObject 已经存在，也未必表示界面已经可见、可交互。到达判定必须与 UI 的实际生命周期对应。

长流程还需要能被取消，并有明确的运行中、完成和失败状态。否则一旦卡在中间，使用者只能猜测是在等资源、没有找到按钮，还是某个前置条件没有满足。

编辑器入口与外部入口共用执行能力

工具后来通过本地 HTTP Bridge 暴露 Unity 内部操作，再由独立的 MCP Server 对接外部客户端。编辑器面板与外部入口最终使用同一套操作能力，不需要各自维护一套点击逻辑。

这个边界也有实际意义：网络请求处理与 Unity 对象访问处在不同的执行环境，访问场景对象、UI 和编辑器状态的部分仍然需要回到 Unity 主线程。Bridge 负责把请求交给合适的执行位置，再把结果返回出去。

进入 Play Mode 也不是一个瞬间完成的调用。执行任务需要跨过模式切换和初始化过程，所以外部调用更适合启动一个任务，再查询它的进度，而不是让一次同步请求无限等下去。

普通开发者未必需要了解这些接口。日常使用时，在窗口里搜索目标界面并运行就够了；外部接口则给批量调试和进一步的自测留下入口。

导航工具能够证明什么

这套工具在我日常工作中最常用的场景，仍然是快速进入游戏并到达待调试界面。它减少的是操作路径上的重复劳动。

到达界面之后，按钮状态、数据正确性、动效以及网络行为仍然需要各自的验证。导航成功不能直接等同于功能测试通过，也不能证明所有设备上的视觉表现都正确。

如果要继续接自动化测试，我会让路由负责“到哪里”，让断言负责“到了之后检查什么”。这样页面入口变动时只修改导航，业务判断也可以独立维护。

从第一版自动点击到后来的导航图，需求始终来自重复发生的小操作。先把最稳定的部分配置化，再随着使用范围扩大补充状态和外部接口，比一开始就规划完整测试平台更符合这次工具的演进过程。

项目地址：Unity-Autorun-MCP。仓库持续更新，安装方式和接口名称以对应版本的 README 为准。
