掛機即可使用的延時攝影All-In-One工作流

發表於 2026-09-06 分類於 攝影技術 閱讀次數：

我把延時攝影中反覆手動完成的操作，做成了一套以 TimelapseManager 為入口的自動化工具流：配置好相機、依賴和拍攝時段後，創建任務就能自動拍攝包圍曝光序列、下載照片、合成 HDR、去閃並導出視頻。開啟晚霞評分後，它還會找出霞光片段、給相冊評分，並通過企業微信推送結果。

這套工具已經能夠運行單次、每日循環和持續分批任務。拍攝、HDR 合成與評分可以並行推進，關閉管理窗口後，後臺任務仍然繼續。本文重點介紹最終能得到什麼，以及支撐這套自動化的任務模型、圖像處理和異常恢復設計。

運行總覽將任務、狀態、當前階段和工作進程放在同一個界面中；圖片來自倉庫隨附的界面演示，任務數據用於展示。

1. 一次任務，得到成片和可篩選的素材

以固定機位拍攝黃昏為例，我希望在設置好時間後，程序完成以下工作：

能力 最終得到的結果
定時拍攝與下載 按曝光組連續編號的本地照片序列
曝光融合與去閃 融合後的 HDR 畫面，以及經過亮度平滑的成片輸入
視頻編碼 H.265 編碼的 MP4 延時視頻
可選的晚霞分析 每個採樣點的分數與理由、最高分照片、晚霞區間
歸檔與通知 按日期和時段組織的相冊、最高分目錄標記、文本與圖片通知

假設一次任務從 16:00 拍到 20:00，每六秒拍攝一組三張照片，理想情況下約產生 2400 組、7200 張 JPG。每組融合為一幀，按 30 fps 編碼後，四小時的變化就壓縮為約 80 秒。這是素材量與成片時長的估算，實際幀數會受曝光、下載耗時和中斷影響。

處理過程中還會生成原始曝光組和 hdr_deflick 去閃中間幀，是否繼續保留由任務清理配置決定。這樣既能直接查看視頻，也能保留值得進一步後期的 HDR 序列。

2. 系統架構：一個入口，分工明確的工具

所有項目都放在 GitHub 的 Hanwen Photograph 組織中。TimelapseManager 同時提供 GUI 與 CLI，倉庫名仍為 Timelapse-Auto-Script。

Manager 承擔任務調度、進程管理、進度彙總和結果處置，圖像處理交給專門的工具。各層通過命令行、文件和公開事件協議連接：

    UI["TimelapseManager GUI / CLI"] --> M["任務服務與後臺 worker<br/>配置、調度、進程、日誌"]
    M -->|啟動與監控| C["Camera Timelapse Controller<br/>gphoto2 控制相機"]
    M -->|啟動與監控| B["Bracketlapse<br/>可選對齊與 enfuse 曝光融合"]

Bracketlapse 負責組織曝光融合、去閃和編碼；SunsetScore 負責目錄採樣、模型推理和評分彙總。Manager 通過它們的公開接口安排工作，各工具可以獨立運行，也可以繼續替換或改進內部實現。

組織裡的 Lumalapse 和 NEF Filter 提供 RAW 精細後期、篩片後整理兩條配套路徑，目前獨立使用。自動拍攝主線直接連接相機控制、Bracketlapse 和 SunsetScore，Simple Deflicker 作為 Bracketlapse 的後期依賴參與處理。

3. 任務管理：讓“一鍵啟動”能夠持續運行

用預設生成明確的任務

Manager 提供四類創建預設，覆蓋臨時拍攝、每日定時和長期記錄：

預設 使用場景 執行方式
manual 明確指定某一天、某個時段 填寫目錄、起止日期和時間、拍攝間隔
scheduled_once 拍攝下一個清晨或黃昏 按項目配置生成一次任務
scheduled_loop 每天重複拍攝 每輪結束後自動生成並啟動後繼任務
eternal 持續記錄 按完整曝光組分批歸檔，後臺依次處理批次

定時預設在創建時會展開為參數明確的 manual 任務，循環預設額外攜帶任務鏈信息。每一輪都擁有自己的時間範圍、輸出目錄、狀態與日誌，發生問題時可以定位到具體一次拍攝。

永續模式則把素材按完整曝光組切成批次，讓拍攝繼續生產新照片，後臺依次處理已經歸檔的批次。批次邊界使用曝光組，避免把同一組中的三張照片拆到不同目錄。

界面與執行進程分離

GUI 和 CLI 共用任務服務，實際拍攝由獨立的後臺 worker 執行。任務定義與運行狀態分別持久化：

因此關閉 GUI 不會結束正在運行的拍攝，重新打開後可以繼續查看和控制任務。啟動前會校驗配置和依賴，並通過啟動鎖與任務狀態檢查阻止同一任務重複啟動。

停止也有不同語義：提前結束拍攝並完成已有素材的處理、當前任務或批次結束後停止，以及立即停止。對於一段正在記錄的黃昏，這些選擇分別對應不同的素材和後期邊界，不能都等同於結束進程。

4. 圖像處理：從包圍曝光到穩定的延時畫面

曝光組是拍攝與處理的交接單位

Camera Timelapse Controller 通過 gphoto2 控制相機，默認使用相機已設置的 AEB 狀態完成三張包圍曝光，也支持逐張改變曝光補償的手動模式。

Bracketlapse 倉庫中的 Nikon Z30 設置照片，展示三張包圍曝光的配置入口；參數為示例。

下載文件採用“組號 + 組內編號”命名。例如一組照片為 0001_01.jpg、0001_02.jpg 和 0001_03.jpg，已有目錄可以從現有最大組號繼續編號。這個命名同時為後期提供了明確的分組協議。

Bracketlapse 接受一組輸入需要滿足兩個條件：成員從 01 到 N 齊全，且文件在連續掃描中保持穩定。captXXXX.jpg 一類臨時下載文件、不完整組都會被忽略。即使某組缺少一張照片，後面的組也能按組號繼續處理。

任務的 processing.group_size 定義 N，未單獨配置時使用 eternal.images_per_group。這裡必須與實際拍攝張數一致。

把拍攝與下載耗時計入間隔

拍攝間隔指相鄰兩組開始時間的目標間隔。以六秒為例，如果拍攝與下載用了三秒，就再等待約三秒；若已經超過六秒，則記錄警告並立即進入下一組。

融合、去閃與編碼分別處理什麼

Bracketlapse 使用 Hugin 的 enfuse 將不同曝光的照片融合成一幀，讓同一畫面裡的亮部和暗部獲得更合適的表現。相機發生輕微位移時，可以額外啟用 align_image_stack 對齊。

曝光融合解決單幀的明暗取捨，延時播放還需要處理相鄰幀之間的亮度跳變。Simple Deflicker 對序列建立亮度直方圖，用滑動平均得到目標分佈，再通過直方圖匹配平滑全局閃爍，同時容納日落過程中的漸變。

這部分基於 struffel/simple-deflicker 上游維護，我的分支補充了直方圖平滑調整、CLI 構建與 macOS 支持。它處理 JPG/PNG 的全局亮度閃爍，室內燈光產生的滾動條紋不屬於該算法的處理範圍。

最後，FFmpeg 從去閃後的幀生成 H.265 MP4。本文所說的 HDR 指包圍曝光融合的畫面效果，是否輸出 HDR10、HLG 等視頻還取決於色彩與編碼鏈路，不能僅由 enfuse 和 H.265 判斷。

這種協作包含兩種粒度：曝光組完成後可以立即融合、增量評分；去閃和最終視頻編碼則在 HDR 生產結束後收尾。評分可以與後期收尾並行推進，最終素材處置再使用完整結果。

進度來自各階段的實際結果

拍攝、HDR、評分和視頻分別記錄進度。視頻階段使用 FFmpeg 的 video_started、video_progress、video_completed 事件，包含已完成幀數與總幀數；成功退出後才發出完成事件。

因此界面能反映“拍攝仍在繼續，HDR 已處理多少組，視頻正在編碼多少幀”。不同設備上的吞吐仍取決於曝光時間、下載速度、CPU/GPU 與磁盤，這種並行設計減少等待，但不承諾固定的實時處理速度。

6. 本地視覺評分與素材保留

從單張分數得到晚霞區間

SunsetScore 使用本地 Qwen3-VL 模型和 llama.cpp 運行時。模型選擇視覺類別，程序再將類別映射為 0—5 分，儘量保持分數與理由一致。首次準備好資源後可以離線評分。

默認間隔為十張，對應第 1、11、21、31……張照片。分數主要描述可見雲層的霞光著色：普通白雲、純日落或暖色地平線不足以達到晚霞閾值；著色明確的雲層可達到 3 分，顏色強烈或覆蓋廣的雲層獲得更高分。

只要任意一個採樣點達到 3 分，就返回 has_sunset = true。相鄰高分採樣點合併為晚霞區間，低分或失敗位置拆開區間。平均分與最高分用於描述結果，其中最高分也用於相冊命名。

選擇“任意一個明確樣本”作為判定依據，是為了保留短暫出現的霞光。即使四小時中的大部分時間都是普通天空，也不應讓長時間的低分稀釋那幾分鐘的畫面。抽樣仍可能漏過更短的變化，需要根據拍攝節奏調整間隔。

評分描述視覺特徵，不是概率，也不等於照片的整體攝影價值。模型不讀取地點或 EXIF 時間，視覺上相似的朝霞也可能獲得高分。

把評分變成可解釋的歸檔動作

Manager 使用分析結論決定 HDR 的保留方式：

結果 處理方式
檢測到晚霞 保留 hdr_enfuse，受管日期和時段相冊添加最高分 -Sx 標記
成功評分且未檢測到晚霞 標記 hdr_enfuse，保留三天後再執行清理
分析失敗，或存在失敗樣本且未檢測到晚霞 保留 HDR，報告評分失敗

無晚霞目錄裡會寫入 .timelapse-hdr-enfuse-delete 標記，記錄帶時區的截止時間。Manager 在服務初始化和後續任務列表檢查時掃描 auto_root，檢查頻率最多每分鐘一次，只處理有效標記且已經到期的 hdr_enfuse。如果期間沒有運行檢查，實際刪除會發生在後續檢查時。

三天的窗口為複核和另存素材留下了時間。這個策略只覆蓋被標記的 HDR 目錄，原始照片、去閃中間幀和視頻仍按各自的任務清理配置處理。

7. 長期運行需要的恢復、依賴與通知

後期失敗時保住已經拍到的內容

拍攝、處理和任務完成是不同的狀態。對於有限任務，Bracketlapse 在拍攝期間意外退出，Manager 會記錄需要恢復，讓相機繼續完成拍攝，再從最終照片執行覆蓋恢復處理。

如果有限任務最終仍然失敗，則跳過清理、保留原始照片。評分失敗同樣不能被當作“沒有晚霞”，否則推理故障會錯誤地變成刪圖依據。這兩條規則把素材保護放在任務成功判定之前。

相機控制工具在下載成功後會刪除相機中的對應副本，因此本地下載目錄承擔了原片保存職責，任務的失敗與清理邊界尤其重要。

讓任務使用的依賴可以確定

Manager 將工作流工具、Python 環境和評分資源放在應用的 .timelapse/dependencies/ 下。任務從這套私有目錄解析命令，減少全局 PATH 或不同 Python 環境帶來的差異。

“包管理”頁可以檢查和安裝組件，並對提供構建信息接口的自有工具顯示版本、源碼分支和構建時間。Camera Timelapse Controller、Bracketlapse、SunsetScore 更新時可以選擇分支，便於確認一次任務實際使用的工具版本。

GUI 支持 Windows、macOS 和 Linux，實際相機控制還取決於 gphoto2 在對應平臺對相機的支持。當前主流程要求 Bracketlapse 至少為 0.4.1，可選 SunsetScore 至少為 0.12.0。

在電腦之外查看拍攝結果

企業微信 Webhook 可以發送任務狀態、評分摘要和最高分照片。運行日誌用於定位過程中的問題，通知則讓完成結果直接到達日常查看消息的地方。

配置頁支持文本與圖片測試，截圖中的機器人地址使用 YOUR_KEY 佔位。

8. 配置一次，重複使用

第一次使用時，先在“包管理”中準備相機控制和後期組件；需要評分時，再準備 SunsetScore 與模型資源。隨後通過“配置中心”確認輸出目錄和時段，“任務管理”負責創建和啟動任務。

9. 兩個配套工具：精細後期與 RAW 整理

對於需要逐段調整畫面的素材，Lumalapse 提供 RAW 序列導入、曝光曲線、關鍵幀調色和視頻導出。它通過 LibRaw/rawpy 在線性空間解碼，在 log2 亮度域計算曲線，將平滑目標與實測曲線之差作為逐幀 EV 補償，再疊加人工關鍵幀曝光調整。

這種方式將去閃與人為設計的明暗漸變結合起來，同時保留高光、陰影、色溫等調整能力。分析結果和關鍵幀緩存到素材目錄中的 .lumalapse/，便於重複打開繼續編輯。

NEF Filter 則把 JPG 篩片結果應用到 Nikon RAW：查找沒有對應 JPG 的 NEF，默認展示刪除列表並等待確認。它支持分別指定 JPG 與 NEF 目錄，默認非遞歸掃描，適合篩片後的整理工作。

兩者是獨立使用的配套工具。自動主線負責從拍攝到初步篩選，值得繼續處理的素材可以進入更精細的後期與整理過程。

10. 演進與版本依據

這套實現主要經歷了三個階段：6 月先補齊相機控制、包圍曝光合成和去閃等單項能力；7 月用任務管理器、圖形界面和晚霞評分建立統一入口；8—9 月完善增量處理、常駐模型、故障恢復與延遲清理。演進最終落在三個設計選擇上：以完整曝光組交接數據，以獨立任務記錄運行，以明確的處理結果決定歸檔。
