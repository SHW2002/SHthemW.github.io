Extending Luban Exports with Generated Business IDs

Posted on 2026-02-02 In 游戏开发 Views:

Typed configuration tables still leave numeric IDs scattered through business code. Looking them up is slow, copying them is error-prone, and handwritten constants add another data source to maintain.

In September 2025 I added item ID generation to our export flow. By early 2026, entities, UI, and audio needed the same support, so I extracted shared output logic and added NPC IDs.

Make tables the single source of data

This does not replace Luban’s data export. Luban parses tables and exports data first; our own post-processing reads the results and generates business constants.

Values still come from the table; constant names provide readable access. Editing generated files is pointless because the next export overwrites them. Their headers explicitly mark them as generated.

Constraints on generated names

The project used “system name + pinyin of the Chinese name” for item constants. This reduces collisions across systems and provides recognizable completion suggestions after entering a system prefix.

Before generation, validate that each system field corresponds to a valid enum. An unknown value should identify the problematic data during generation, rather than produce an apparently normal constant with unclear meaning.

Chinese names can still collide after pinyin conversion, so the implementation tracks used names. A later duplicate gets its data ID appended, accompanied by a warning.

This is practical compatibility handling, not a guarantee of permanent names. Wording changes or a different order of duplicate entries can change the result. Long-lived references are better served by a separate code-name field, maintained independently from display text.

Pinyin is also not complete C# identifier sanitization. The project’s naming conventions cover everyday data, but arbitrary punctuation, leading digits, and keywords do not automatically become valid code. Handle these cases through input constraints or the generator, then verify through compilation.

Output repeats; table rules vary

As generators multiplied, parameter checks, namespace creation, comments, constants, and directory creation became repetitive. Every new table copied much the same file-writing logic.

I split it into two layers:

Layer Responsibility
Per-table generators Read data, select entries, validate business fields, and choose names
Shared base class Organize C# structure, generate comments, emit constants or enums, and write files

The upper layer supplies simple entries: constant name, ID, and description. A new table then focuses on which entries to generate and what to call them, without maintaining file formatting again.

This shows the responsibility structure and omits project-specific data types. Constants and enums can have separate output entry points; consistency does not require forcing every table into the same declaration form.

Discover and execute generators

All generators live in one tooling assembly. The loader uses reflection to find non-abstract subclasses of the shared base, selects those with parameterless constructors, then instantiates and executes them together.

Sorting by type name makes execution order deterministic. That order keeps behavior predictable but should not encode implicit dependencies. If B must read A’s result, arrange that dependency explicitly.

A common entry point also supports output to different code modules: table-reading and naming rules are reused, while each generator supplies the namespace, class name, and destination.

This implementation records an individual generator’s exception and continues trying the others. That reveals several problems in one run, but later successful tables do not mean the whole export succeeded. Automated builds must aggregate errors and fail instead of using incomplete output.

The generated content itself must be stable for this comparison to help. Do not add the current time to every output or rely on unordered collections for entry order. Unchanged inputs and rules should produce identical text on repeated runs.

Which problems constants expose early

Named constants make missing symbols after configuration deletion or renaming visible during compilation. Their comments also explain what the data means.

Constants only cover references visible at compile time. IDs received over the network, old IDs in saves, and resource relationships constructed at runtime still need data validation. Generated code does not prove every configuration reference valid.

Another detail is that C# const values are inlined into callers at compile time. If the constants assembly and its consumers are updated separately, rebuild the consumers too; replacing only the defining assembly is insufficient.

Turn conventions into an executable workflow

The immediate benefit is eliminating handwritten numeric IDs and giving new table types the same generation entry point. Central naming and validation rules provide a clear place for future changes.

I retained each table’s own selection and naming logic and unified only repetitive output. That boundary is practical for project tooling: generators encode the rules, export produces the result, and compilation plus resource integration check it.
