Dynamic Registration and Favorites for Game GM Tools

Posted on 2025-03-19 In 游戏开发 Views:

As gameplay grew, our GM panel accumulated more buttons. Keeping commands on one page worked at first, but finding an uncommon operation became slow, and adding one often meant editing the panel itself.

In August 2024 I added categories and runtime registration; in March 2025 I added local favorites. These small changes addressed a daily development and testing problem.

Represent commands as data

First, extract command management from the panel class. A command needs at least a name, category, and execution function. Some button names change with the current state, so a function can also supply the name.

Here is a simplified Lua structure:

Each business module registers the commands it actually needs, and the panel creates buttons from that data. Adding categories or operations no longer requires appending logic to the same UI file every time.

The manager stores lists by category and maintains a name index. Registration checks for duplicates; execution catches exceptions and records results centrally. The panel handles parameter input, button display, and user interaction.

Categories help discovery; favorites help repeated use

Categories and favorites serve different situations. Someone who does not know where a command lives can browse by business category. Someone who already knows a command and uses it every day needs a fixed entry point.

A diagram redrawn from the original functionality; all command names are generic examples.

Favorites are saved locally and restored from registered commands after restarting the game. Testers no longer need to find the same few buttons every morning. I also added duplicate checks and persistence cleanup after removal, keeping the displayed panel consistent with what would be restored on the next launch.

Categories improve a person’s search path. This should not be described as a definite reduction in algorithmic complexity: the command count, category structure, and usage habits all affect the actual experience.

Favorite references need stable identifiers

This version finds favorites using command name keys. It is easy to integrate, but has limitations: a function-generated name may change with state, and renaming a button for clearer wording may break an existing favorite.

For future tools, I would separate a stable ID from the display name:

This is an improvement direction for the original implementation, rather than a capability already included in this release. Favorites would store only IDs, allowing names to change. An ID would also make it possible to recognize that a runtime command had been removed.

Restoration timing matters too: wait for business modules to finish registering before resolving favorites. Clearing every unresolved entry before registration would also discard commands belonging to modules that simply have not loaded yet.

Centralize exception handling at the execution entry point

The panel does not need separate exception handling for every button. A Lua manager can wrap execution in xpcall, report success or failure consistently, and refresh button names that may depend on state.

This wrapper mainly covers synchronous execution. If a command starts another coroutine or waits for an asynchronous callback, subsequent failures still need their own asynchronous result handling. Returning from the outer function is not sufficient reason to display “Operation complete.”

Once registration, presentation, execution, and favorites each have a clear responsibility, the tool becomes easier to extend. The real test is how many places the next colleague must edit to add a command, and how quickly users can find it.
