The Evolution of Unity-Autorun-Tool (2026)

Posted on 2026-08-12 In AI技术 Views:

At the end of 2024, I built a small Unity auto-clicking tool. Every time I entered the game, I had to wait for the scene to load, then click through the connection, login, and entry buttons. This took about half a minute. It was simple, but having to watch the whole process was inconvenient.

As AI technology developed, I felt this automation could provide useful scaffolding for AI agents. I gradually added UI navigation, an editor entry point, and a command-line interface, with the goal of delivering an MCP tool for AI agents.

Initially, I only wanted presets to handle those clicks. As more interfaces needed testing, the tool grew to let me prepare paths between them, select a target during everyday debugging, and have the program handle the navigation in between.

The first version handled fixed steps

The first version’s basic features were completed in November 2024, followed by actions to run before exiting and usage instructions. Each preset stores a sequence of operations, with these main fields:

Field Purpose
Button name Locate the object to operate on
Button text Distinguish buttons with the same name when necessary
Wait time Wait for a scene or interface to become ready
UI framework Select the handling for UGUI or FairyGUI

Running the tool enters Play Mode and then executes the configured operations in order. The Stop actions added later run before stopping the game, such as leaving the current room before ending a debugging session.

This version did not shorten the game’s loading time. It removed the need for me to perform several actions while waiting, so I could do something else during loading.

The same mechanism was later used in several projects. Their login flows differed, but adjusting the presets avoided having to write another set of editor buttons for each project.

From operation sequences to interface relationships

Sequential presets work well for fixed entry paths, but two problems emerge as the number of interfaces grows.

First, multiple targets share the first part of a flow. Opening the inventory and opening settings both require reaching the main interface. Copying a complete sequence for each target means a change to the login flow must be propagated across many presets.

Second, execution does not always start from the same place. The game may not yet be in Play Mode, it may already be at the main interface, or it may be displaying a popup. A list of button names alone struggles to express these differences.

I therefore started describing the UI with a navigation graph, separating the information into views, controls, transitions, and routes:

Concept Information recorded
View An identifiable interface or panel
Control A button or another control used for navigation
Transition An operation that takes the UI from one view to another
Route A reusable navigation path

A simplified illustration with interface names independent of any particular project. The shared login flow only needs to be maintained once.

An edge in the graph cannot merely say that the inventory can be opened from the main interface. It must also identify the control to use, the condition that confirms arrival, and whether the prerequisites for execution are met in the current environment.

Finding a call that opens an interface in the source code establishes a possible connection, but it does not mean the automation tool can immediately follow it. The entry may be restricted by level requirements, or an asynchronous operation may need to finish first. These gaps must remain visible rather than being treated as verified paths.

AI helps prepare the graph; the program runs everyday navigation

Projects contain many UI calls, and manually assembling a complete navigation graph takes effort. I use AI to help analyze interface relationships in the source code, organize candidates into navigation data, and then check them against what the tool can recognize and execute.

The work is divided into two stages:

  • Preparation: understand the code and interface semantics, then generate or revise the navigation graph.
  • Execution: read the prepared graph, run defined steps, wait for results, and report status.

Once a path is ready, clicking an editor button or running a command does not require the model to make a fresh decision at every step. Here, “offline navigation” means that execution does not depend on AI inference; the game itself may still need a server connection.

This also defines the maintenance work: update the relevant data when interface structures or transition logic change, and reuse paths that remain unchanged. The navigation graph is tool data that must be maintained alongside the project, rather than something generated once and valid forever.

Completing a click and completing navigation are different events

Early sequential presets relied mainly on wait times, but fixed delays have clear limitations. As machine load, resource caching, and network responses change, the same two-second wait may be too short or unnecessarily long.

Navigation execution is better organized around state:

Sending a click only means the operation was performed; it does not mean the target panel is open. Conversely, the existence of a GameObject does not necessarily mean its interface is visible or interactive. Arrival checks must match the UI’s actual lifecycle.

Long flows also need cancellation and clear running, completed, and failed states. Otherwise, when execution gets stuck, the user can only guess whether it is waiting for resources, unable to find a button, or missing a prerequisite.

Editor and external entry points share the same execution capabilities

The tool later exposed operations inside Unity through a local HTTP Bridge, with a separate MCP Server connecting external clients. The editor panel and external entry points ultimately use the same operations, avoiding separate implementations of the click logic.

This boundary has practical consequences: network request handling and Unity object access run in different execution contexts. Access to scene objects, UI, and editor state still needs to return to Unity’s main thread. The Bridge passes each request to the appropriate execution context and returns the result.

Entering Play Mode is also not an instantaneous call. Tasks must survive the mode switch and initialization, so an external caller is better served by starting a task and querying its progress than by waiting indefinitely in a synchronous request.

Most developers do not need to understand these interfaces. For everyday use, searching for a target interface in the window and running navigation is enough. The external interfaces provide entry points for batch debugging and further automated testing.

Setup and use

The tool provides installation through UPM, Bridge and MCP management inside the editor, and runtime UI state inspection. You can set it up from the editor panel, then run navigation and state checks.

Open the tool from the editor

The tool requires Unity 2021.3 or later. Install it through Package Manager using Add package from git URL...:

After installation, open Window > Auto Run Window. If you only use manual presets, you can configure Go and Stop actions directly. CLI or MCP integration also requires the .NET 8 SDK.

The MCP panel from the README, with installation paths and process IDs hidden.

Publish MCP generates the server application, Install MCP installs connection settings for the selected client, and Install Skill installs the accompanying workflow. Once the Bridge panel shows Running and recognizes the client process, generate or update the navigation graph.

The Bridge port may change if a port is occupied. External entry points read the endpoint published by the current Unity project; the example port 17331 should not be treated as a permanent fixed port for every project.

Calling start_ui_navigation from an external client returns a navigationId. Use get_ui_navigation_status to query the final state. This keeps startup, login, and intermediate waits inside the tool, so the external caller does not need to keep listing buttons again.

The README also provides Preview Nav Map, which uses the bundled Graphviz to render an interactive local HTML page. It supports searching for views, inspecting adjacent paths, zooming, and panning. If navigation fails, first check whether the target is reachable, then whether the relevant edge has the conditions needed to execute its operation.

Inspect UI state after arrival

get_ui_state reads text, active state, and interaction properties from UGUI and TextMeshPro controls. wait_for_ui_state checks a condition until it is met or the request times out. Support for clicking FairyGUI buttons does not imply that every FairyGUI control supports the same typed state inspection; use the capabilities the tool actually provides.

What navigation and assertions can establish

The most common use of this tool in my everyday work is still entering the game quickly and reaching the interface I need to debug. It reduces repetitive work along that path.

After arrival, button states, data correctness, animations, and network behavior still need their own verification. Successful navigation cannot be equated with a passing functional test, nor does it prove that the visuals are correct on every device.

Runtime assertions assign “where to go” to routes and “what to check after arrival” to state conditions. When an entry point changes, only the navigation needs updating, while business checks can be maintained independently. Even when control text and state satisfy their conditions, they still cannot directly establish that animations and visuals are correct on every device.

From the first auto-clicking version to the later navigation graph, the requirements always came from small, recurring operations. Configuring the most stable parts first, then adding state checks and external interfaces as usage expanded, better matched this tool’s evolution than planning a complete testing platform from the start.
