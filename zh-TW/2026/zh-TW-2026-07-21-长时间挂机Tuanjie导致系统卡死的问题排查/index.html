團結引擎長時間掛機導致系統卡死的問題排查

發表於 2026-07-21 分類於 遊戲開發 閱讀次數：

這兩天用Tuanjie開發項目, 掛機一段時間之後電腦總是莫名其妙的卡死(通常是第二天上班發現)，沒藍屏，也沒有穩定的報錯彈窗, 只偶爾會有幾個應用程序報錯提示OOM, 一旦出現基本只能長按電源鍵重啟。

最後排查出是 Tuanjie 內存洩漏，Unity 6 也存在。但通過一些特殊途徑可能更高頻地觸發內存洩漏，導致卡死，在此記錄一下排查的過程。

環境

  • 操作系統：Windows 11
  • 編輯器：Tuanjie 2022.3.62t6
  • 構建分支：tuanjie/1.8/staging

日誌

因為出問題的時候系統基本卡死了, 所以除了Tuanjie 自己的日誌, 我也看了下系統的崩潰日誌, 有沒有哪個子進程崩潰前有比較異常的情況.

直接讓GPT給我掃了一下盤, 一週內共找到 60 條資源耗盡事件，最關鍵的是 Event ID 2004, 官方文檔和信息描述都提示了確實是內存不足導致的崩潰:

這些事件的成因並不完全一樣:

  1. 有一次，Tuanjie 私有內存從約 35.18 GiB 漲到 39.25 GiB，嫌疑很大。
  2. 另一次，系統提交量達到約 94.93/94.94 GiB。
    • svchost 漲到 50.74 GiB。
    • DoSvc 相關進程約 12.65 GiB。
    • Tuanjie 約 9.08 GiB。

下面是兩條典型的 Event ID 2004，字節數我自己加了下分隔，方便複核。

導出的系統日誌裡共有 83 條 Event ID 2004，向前篩七天是 60 條。

第一條裡，Tuanjie 確實是最大消費者。

第二條很不一樣，真正吃掉大頭的是 svchost。

這就有點麻煩了：Tuanjie 有嫌疑，但不是每次 OOM 的唯一答案, 可能最終的崩潰是由多個內存洩漏的Bug導致的. 我們這次的目標是先把影響最大的搞掉, 至少讓編輯器不要掛機太久就崩潰

排查工具

讓AI搓了個MemoryLeakTracker, 大體功能是當系統內存在一段時間內異常增長時, 採集以下信息:

採集內容 工具 規則
系統內存和內核池 性能計數器 15 秒一次，循環保存
Tuanjie 內存、句柄和線程 性能計數器 達到閾值時留檔
句柄、堆和虛擬內存棧 WPR/ETW 保存約 10 分鐘 ETL
進程現場 ProcDump 私有內存到 12 GiB 時轉儲
輔助證據 事件日誌和系統快照 事件前後各保存一份

滿足以下條件之一就會觸發這個採集器：

  • Tuanjie 私有內存超過 6 GiB
  • 系統提交率超過 70%
  • 句柄超過 10,000
  • 10 分鐘內增長超過 768 MiB
  • 私有內存達到 12 GiB 時生成轉儲

這個工具並不解決系統會崩潰重啟的問題, 只要死之前能留下遺言就夠了 (悲) 這樣我下次登錄的時候就有希望看到更具體的日誌。如果沒有 ETL 和轉儲，只能得到一句“佔用很高”這種正確的廢話, 然並卵。有了調用棧，才有機會追到 DuplicateHandle 的上層。

問題復現

工具做好之後直接重啟掛機了一段時間, 很意外的是才沒過幾分鐘工具就彈窗提示開始記錄了. 看來平時崩潰幾天才出現一次或許是因為這臺電腦有64G的物理內存能硬抗一段時間.

1. 復現

第一份關鍵採集位於：

E:\MemoryLeak-Capture\Incidents\20260720-142209-PID22848

14:21:19，兩個 AssetImportWorker 啟動。

14:22:09，其中一個工作進程達到約 11,590 個句柄，自動採集被觸發。

自動生成的 incident-20260720-142210.json 中，關鍵字段如下：

當時系統提交率只有 29.05%，並不是正在發生的 OOM，而是追蹤器提前抓到了異常行為。

主進程的句柄變化非常典型, 基本就是一個上升-下降的鋸齒狀曲線, 然後毫不令人意外的是每次鋸齒之後的量會比上次多一些：

時間 主進程句柄數
14:22:10 6,060
14:24:18 35,684
14:29:57 120,037
14:30:29 8,846
14:38:51 132,168

14:59:59 到 15:00:04，只有 5 秒，句柄卻從 14,884 漲到 16,825，私有內存仍在約 4 GiB。

這裡已經基本可以確定排查方向, 洩露的不是堆內存而是句柄。

2. 分析

接著用 Sysinternals Handle 檢查 PID 27308 (剛才出問題的pid)。

一次快照裡，數據是這樣的：

  • 總句柄數：97,998
  • Thread 句柄：92,490
  • 實際存活線程：289

Handle 工具的關鍵輸出摘錄如下：

九萬多個 Thread 句柄，鼠實有點嚇人。

再按目標線程聚合，超過 99% 的異常句柄都指向 TID 30960, 也就是說這一坨句柄其實都是這一個線程搞出來的, 實際上系統並沒有開啟那麼多任務.

高度懷疑是這個30960背後的服務被複制或重啟了N次, 導致句柄數量一直在增長.

3. 石錘

為瞭解析 ETL，安裝了 Windows Performance Toolkit, WPAExporter 加載了微軟符號和 Tuanjie 符號。

只看 15 秒，同一條複製棧就出現了 219,368 次，這個數字已經離譜了。

WPA 導出結果的聚合摘要如下：

到了這裡，基本可以說是破案了：

  1. PreviewTextureManager 的後臺加載線程正在執行預覽任務。
  2. 它通過 ProtectedScopedThreadAttach 把原生線程附加到 Mono。
  3. Mono 會複製原生線程句柄。
    • 調用點：mono_threads_open_native_thread_handle
  4. 句柄沒有被及時關閉，同一個線程對象越積越多。

根因其實還是落在 Tuanjie 引擎內部，位置是預覽線程與 Mono 附加路徑。

為什麼這個項目特別容易觸發

“誰在漏”已經找到了，但事情還沒完。同一個引擎，為什麼這個項目觸發得這麼頻繁？

編輯器日誌顯示，在異常開始前後，下面這個文件被反覆檢測、寫入和導入：

順著日誌和代碼排查，發現其實是ThunderFire UXTool的收藏夾功能引發的頻繁寫入：

  1. RecentSelectRecord 訂閱 Selection.selectionChanged。
  2. 每次選擇改變時，代碼會先刪除舊記錄，再添加新記錄。
  3. 刪除和添加都會調用 JsonAssetManager.SaveAssets。
  4. SaveAssets 把 JSON 寫進 Assets 目錄。
    • 寫入接口：File.WriteAllText
  5. 寫入會觸發 Asset Database 刷新。
  6. “最近選中”界面的資源項還會調用 AssetPreview.GetAssetPreview。
  7. 這些預覽請求最終進入正在洩漏的 PreviewTextureManager。

重啟前的 Editor-prev.log 也對上了。下面只截一小段：

prematurely finalized 和句柄驟降能對上。終結器會回收一批對象，但同一條創建路徑還在跑。

關鍵源碼位置包括：

  • RecentSelectRecord.cs：訂閱選擇變化以及刪除、添加記錄
  • RecentFilesSetting.cs：每次修改後立即保存 JSON
  • AssetItemMatFile.cs：請求材質預覽
  • AssetItemOthersFile.cs：請求其他資源預覽
  • SwitchSetting.json：保存“最近選中面板記錄”功能開關

官方問題記錄

Unity 官方 Issue Tracker 裡有一條類似的記錄：UUM-141036。

它的原生調用鏈幾乎一樣：

不過，Tuanjie 是獨立分支，Unity那邊的事情很可能跟我們已經沒有關係了. 目標版本有沒有修好，還得看實際問題有沒有解決。考慮到項目中途升級引擎版本風險很大, 恐怕這個問題要一直陪伴我們很長時間.

15:55:57 6,100 3,711.8 MiB

啟動階段，句柄最高到 7,564，很快又回落到 5,500～6,100

39 秒採樣裡，句柄從 5,831 漲到 5,871，速度約為每秒 1.03 個

過了約 7 分鐘，句柄又從 6,100 回到 6,075

舊進程會每秒漲幾百個，還會衝到十幾萬，看來我們已經解決了引發問題的大頭. 考慮到這是團結自己的問題, 殘留有少許的上漲也不令人意外. 能把崩潰的頻率降低就算成功.

重啟後的 Handle 摘要如下，總量已經回到正常範圍。

2026 年 8 月後續：把正常重啟做成工具

排查之後，我又製作了 Unity-Restart-Tool，用來管理 Windows 上多個 Unity / 團結編輯器實例，並提供手動批量重啟和按項目設置的定時計劃。

工具會識別具有主窗口與有效項目路徑的編輯器，排除 AssetImportWorker 等後臺進程。項目內的 Editor companion 負責檢查當前是否正在運行遊戲、編譯、導入或構建；不滿足條件或無法完成檢查時跳過實例，通過檢查後才嘗試正常退出並重新啟動，不強制結束進程。

另外還有一個短時間的 Console 安靜檢查，退出前會再次檢查編輯器狀態，減少檢查完成到實際退出之間的狀態變化問題。這個檢查只是重啟條件之一，不能證明編輯器或項目本身沒有問題。

這裡有個使用前需要明確的邊界：工具當前沒有把場景與資源的 Dirty 標誌作為重啟門禁，未保存內容可能隨編輯器退出而丟失，所以需要先保存工作，再使用手動或定時重啟。

它是長時間運行時的輔助工具，不是本文引擎問題的修復，也不會改變前面的根因判斷。窗口位置可以嘗試恢復，Unity 內部佈局仍然依賴編輯器正常退出時保存；Windows 任務欄上的精確排列也不能保證完全復原。

總結

總結一下問題的前因後果：

  • 表面現象：系統多次內存耗盡、桌面組件崩潰或整機卡死。
  • 已確認缺陷：PreviewTextureManager 會反覆複製線程句柄，句柄釋放不及時。
  • 項目側觸發器：UXTool“最近選中”會反覆寫 JSON，還會刷新資源並請求預覽。
  • 臨時解決：關閉該功能、正常退出並重啟 Tuanjie。
  • 驗證結果：句柄增速從每秒 380～400 個降到約 1 個。
    • 線程句柄從 92,490 個降到 557 個。
    • 原洩漏特徵消失。
  • 長期解決：等待或驗證 Tuanjie 引擎版本修復，不能把項目側規避當作引擎缺陷已經消失。
