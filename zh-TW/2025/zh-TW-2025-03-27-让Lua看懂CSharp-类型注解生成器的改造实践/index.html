改造EmmyLua(LuaLS)的UnityAPI註解生成器

發表於 2025-03-27 分類於 遊戲開發 閱讀次數：

在 Unity 的 Lua 業務中調用 C#，經常會遇到一種割裂感：代碼運行沒有問題，編輯器卻不知道對象是什麼類型，也無法繼續補全後面的字段。尤其經過單例、委託和 CS 表之後，一條本來有完整類型信息的調用鏈，很容易變成一串未知字段。

我在開源生成器上做了些修改，把這些類型提示補齊。

這批改動從 2025 年 1 月持續到 3 月，最終通過 PR 合併回上游。本文記錄其中幾個最有價值的處理。

工具的 GitHub README，點擊圖片可打開倉庫。

生成註解，並不改變運行時

工具在 Unity 編輯器中通過反射讀取 C# 程序集，再生成 Lua 語言服務能夠理解的類型聲明。註解文件提供給編輯器分析，不應該作為業務腳本被加載執行。

泛型繼承會把類型信息丟在哪

最常見的情況是泛型單例：

如果生成器只看泛型定義，Instance 的類型只能寫成 T。但對 InventoryService 來說，繼承關係已經明確提供了實參，編輯器本來可以知道 Instance 就是 InventoryService。

我補充的處理是：在生成具體派生類時檢查父類的泛型信息，把能夠確定的字段與屬性類型落實到派生類的聲明中。於是調用 InventoryService.Instance.Capacity 時，類型鏈可以繼續下去。

這不是一套完整的 C# 泛型推導系統。這個階段的實現主要覆蓋非泛型派生類、直接父類只有一個泛型參數、繼承字段與屬性的常見場景；多參數映射、複雜嵌套以及方法的泛型參數和返回值仍需另外處理。

把邊界說明清楚很有必要：類型提示在大部分調用鏈上改善，並不意味著所有泛型組合都能正確生成。

類型名與 CS 表的訪問路徑

xLua 中常通過 CS.UnityEngine.Vector3 訪問 C# 類型，但已有註解可能寫成 UnityEngine.Vector3。如果把兩種寫法當成互不相干的類型，賦值與字段訪問就會出現無意義的提示。

工具默認生成正常的類型名，再提供可選的 CS. 前綴兼容聲明。目標是讓這兩種註解寫法描述同一個類型，同時讓訪問 CS 表時能夠獲得成員提示。

這裡要同時關心類型別名和表的字段聲明。僅僅建立一個名稱別名，並不自動保證語言服務在 CS.UnityEngine 這條訪問路徑上能夠繼續識別成員；這也是改造中實際修過的問題之一。

項目需要保留哪種寫法，最好在接入時明確下來，避免生成文件與手寫註解形成兩套相互不兼容的命名習慣。

需要區分的是，類型別名只改變編輯器怎樣理解註解，不會創建新的運行時全局變量。即使啟用了兼容別名，xLua 代碼真正訪問類型時仍然需要 CS.UnityEngine.Vector3；直接寫 UnityEngine.Vector3.zero 不會因為生成了註解就自動可用。

代價是 function 本身比較寬泛，它不能替代精確的參數與返回值檢查。所以兼容列表只應包含運行時確實支持轉換的類型。若某個回調需要嚴格簽名，更合適的辦法是進一步生成明確的 fun(...) 聲明。

靜態方法與實例方法不能混淆

Lua 的點調用與冒號調用在參數上有區別，冒號會隱式傳入 self。如果把 C# 靜態方法生成為實例方法，編輯器看到的參數列表就會錯位。

生成器需要根據反射結果中的 IsStatic 決定聲明方式。我也修復了靜態函數仍然攜帶實例參數的情況，並整理了泛型名稱後綴、匿名類型等不適合直接暴露的類型名稱。

這些問題看起來零碎，但它們決定了使用者能否信任提示。如果日常面對很多錯誤警告，人反而會習慣性忽略真正的問題。

讓生成過程適合反覆使用

除了類型映射，我還補了幾項使用上的功能：

  • 按命名空間選擇要生成的程序集內容，避免把無關類型全部塞進索引。
  • 為 C# 注入的全局變量和 typeof 等入口生成聲明。
  • 按配置行數拆分註解文件，便於管理較大的輸出。
  • 用編輯器窗口保存生成選項，減少每次修改源碼配置的操作。

文件拆分是否改善分析速度，與語言服務和項目規模有關，我沒有做跨編輯器的統一性能基準。更確定的收益是生成範圍和輸出組織都可以控制。

使用 Lua Language Server 時，可以把生成目錄加入 workspace.library。無論文件放在哪裡，都應讓語言服務只索引需要的聲明，避免舊輸出和新輸出同時存在、重複定義同一類型。

生成目錄也應專用。這個工具會清理目標目錄中的舊註解，因此不能把手寫業務腳本和生成文件混放。

將倉庫克隆到 Unity 項目中，等待編輯器編譯後，從頂部的 LuaType 菜單先打開設置，再執行生成。README 中的幾項配置可以按下面的順序準備：

配置 設置方法
配置文件目錄 指向一個可寫目錄；默認值來自 AppDomain.CurrentDomain.BaseDirectory，在 Unity 中可能落到引擎安裝目錄
註解輸出目錄 使用專用目錄，按工具要求以路徑分隔符結尾；不要存放業務文件
C# 命名空間 根據項目引用補充，用空格分隔，例如 DG FairyGUI

生成後先找一條真實調用鏈驗證：能否識別 CS 下的類型、泛型單例後的成員，以及委託參數接受 Lua 函數時的提示。新增程序集、調整生成選項或 C# API 變化後，再重新生成對應的聲明。

不同語言服務對註解的兼容細節可能不同，README 所說的 EmmyLua 與 SumnekoLua / LuaLS 支持，並不意味著任意版本組合都完全一致。接入時用項目實際使用的編輯器驗證，比只確認生成了文件更可靠。

從項目改動到上游合併

這次改造建立在原作者的生成邏輯上，我主要補充了項目實際需要的能力與問題修復。提交上游時，把新增選項、兼容範圍和使用說明一起整理，比只提交一份能在自己工程裡運行的腳本更容易讓其他人理解。

PR #2 於 2025 年 3 月 27 日合併。工具倉庫：EmmyLua-Snippet-Generator；原項目：EmmyLuaXLuaSnippetGenerator。

跨語言類型提示的價值，首先體現在日常寫代碼時少一點猜測。把運行時已經掌握的類型信息傳給編輯器，就能讓調用鏈、參數和字段更早暴露問題；但最終執行是否合法，仍然要由真實的運行時規則與測試確認。
