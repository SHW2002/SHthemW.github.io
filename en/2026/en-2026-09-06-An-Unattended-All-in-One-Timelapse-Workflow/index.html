An Unattended All-in-One Timelapse Workflow

Posted on 2026-09-06 In 摄影技术 Views:

I built an automated workflow around TimelapseManager: configure the camera, dependencies, and schedule, then create a task to capture brackets, download photos, fuse HDR, deflicker, and export video.

Optional sunset scoring finds colorful intervals, rates albums, and sends results through WeCom.

The tools now support one-off, daily recurring, and continuous batch tasks. Capture, HDR fusion, and scoring can run concurrently, and background tasks continue after the management window closes. This article focuses on the outputs and the task model, image processing, and recovery design behind the automation.

The overview puts tasks, states, current stages, and workers in one interface. It comes from the repository’s UI demonstration; task data is illustrative.

1. One task produces a video and selectable source material

For a fixed camera recording dusk, I want the program to perform these operations after I set the schedule:

Capability Result
Scheduled capture and download Local photo sequences numbered by exposure group
Exposure fusion and deflickering Fused HDR frames and brightness-smoothed video input
Video encoding An H.265-encoded MP4 timelapse
Optional sunset analysis Scores and reasons per sample, the highest-scoring photo, and sunset intervals
Archiving and notifications Albums organized by date and time, maximum-score directory labels, and text/image notifications

Suppose a task runs from 16:00 to 20:00, capturing a three-photo group every six seconds. Ideally it produces about 2,400 groups and 7,200 JPGs. Fusing each group into one frame and encoding at 30 fps compresses four hours into about 80 seconds. These are material-count and duration estimates; exposure, download time, and interruptions affect the actual frame count.

Video and album output

S4 on date and time directories makes valuable periods visible in the file manager. When several marked albums share a day, the outer date directory uses their maximum score.

Processing also produces original exposure groups and intermediate hdr_deflick frames. Task cleanup settings determine whether to retain them, allowing direct video review while keeping HDR sequences worth further editing.

Sunset selection results

These actual SunsetScore examples come from the same timelapse sequence. Ordinary white/gray clouds score 1, softer colored clouds score 3, and widespread vivid cloud coloring scores 4.

Original score labels are retained, arranged from low to high. This example set contains no score-5 photo.

For daily fixed-camera recording, selection reduces opening folders and searching frame by frame for sunset color. The video supports a quick review; scores and intervals identify material worth a closer look.

2. Architecture: one entry point, specialized tools

All projects live in the GitHub Hanwen Photograph organization. TimelapseManager offers both GUI and CLI; its repository is still named Timelapse-Auto-Script.

Manager schedules tasks, manages processes, aggregates progress, and handles results. Specialized tools perform image processing, connected through command lines, files, and public event protocols:



flowchart TB
    UI["TimelapseManager GUI / CLI"] --> M["Task service and background workers<br/>Configuration, scheduling, processes, logs"]
    M -->|Launch and monitor| C["Camera Timelapse Controller<br/>Camera control with gphoto2"]
    M -->|Launch and monitor| B["Bracketlapse<br/>Optional alignment and enfuse fusion"]
    C -->|Complete stable exposure groups| B
    B -->|HDR sequence| D["Simple Deflicker<br/>Brightness deflickering"]
    D --> V["FFmpeg<br/>H.265 video"]
    B -->|hdr_ready forwarded by Manager| S["SunsetScore<br/>Persistent local scoring service"]
    S --> A["Manager result handling<br/>Album labels, HDR retention, notifications"]

Bracketlapse organizes exposure fusion, deflickering, and encoding; SunsetScore handles directory sampling, model inference, and score aggregation. Manager coordinates through public interfaces. Each tool can run independently, and its internals can be replaced or improved.

Lumalapse and NEF Filter provide separate paths for detailed RAW editing and organization after selection. They are currently used independently. The main capture pipeline directly connects camera control, Bracketlapse, and SunsetScore; Simple Deflicker participates as a Bracketlapse post-processing dependency.

3. Task management: keeping one-click startup running

Presets create explicit tasks

Manager offers four creation presets for ad hoc capture, daily schedules, and long-term recording:

Preset Use case Execution
manual A specified day and time window Set directory, start/end dates and times, and capture interval
scheduled_once The next morning or dusk Generate one task from project settings
scheduled_loop Daily repeated capture Automatically create and start a successor after each run
eternal Continuous recording Archive complete exposure groups in batches and process them sequentially in the background

Scheduled presets expand into explicit manual tasks at creation; looping presets also carry task-chain information. Each run has its own time range, directory, status, and logs, so problems can be traced to one capture.

Continuous mode divides material into batches of complete exposure groups. Capture keeps producing photos while the background processes archived batches. Group boundaries prevent the three photos of one exposure set from landing in different directories.

Separate the interface from execution

GUI and CLI share a task service; independent background workers perform capture. Definitions and runtime state are persisted separately:

Closing the GUI does not stop capture. Reopening restores monitoring and control. Startup validates settings and dependencies; a startup lock and task-state checks prevent duplicate launches.

Stopping has several meanings: end capture early and process existing material, stop after the current task or batch, or stop immediately. During dusk recording, these choices create different material and processing boundaries; they cannot all be reduced to terminating a process.

4. Image processing: from brackets to stable timelapse frames

Exposure groups connect capture and processing

Camera Timelapse Controller uses gphoto2. By default it captures three brackets using the camera’s configured AEB mode; it also supports manual exposure-compensation changes for individual shots.

The Nikon Z30 settings photo from Bracketlapse shows where to configure three-shot bracketing; values are examples.

Downloads use “group number + member number,” such as 0001_01.jpg, 0001_02.jpg, and 0001_03.jpg. An existing directory can resume from its largest group number. This naming also gives post-processing an explicit grouping protocol.

Bracketlapse accepts a group only when members 01 through N are complete and files remain stable across successive scans. Temporary downloads such as captXXXX.jpg and incomplete groups are ignored. A missing photo in one group does not prevent later group numbers from being processed.

processing.group_size defines N, falling back to eternal.images_per_group when not set separately. It must match the actual number of captured photos.

Include capture and download time in the interval

The capture interval is the target gap between successive group start times. For six seconds, if capture and download take three seconds, wait about three more. If they already exceed six seconds, log a warning and start the next group immediately.

This avoids waiting an additional fixed six seconds after every capture and drifting from the configured cadence. Camera and transfer speed still limit throughput; a smaller setting does not guarantee equally spaced photos at that interval.

Fusion, deflickering, and encoding have different roles

Bracketlapse uses Hugin’s enfuse to combine exposures into a frame with more suitable highlights and shadows. Optional align_image_stack alignment handles slight camera movement.

Exposure fusion handles tonal choices within one frame. Timelapse playback also needs inter-frame brightness consistency. Simple Deflicker builds brightness histograms, derives target distributions with a moving average, then uses histogram matching to smooth global flicker while accommodating the gradual change of sunset.

This work maintains a fork of struffel/simple-deflicker, adding histogram smoothing adjustments, CLI builds, and macOS support. It handles global JPG/PNG brightness flicker, not rolling bands from indoor lights.

FFmpeg finally creates an H.265 MP4 from deflickered frames. “HDR” here describes the fused bracketed imagery. HDR10 or HLG video output depends on the color and encoding pipeline; enfuse and H.265 alone do not establish it.

5. A parallel pipeline: capture, fuse, and score concurrently

Completed groups can enter processing immediately during long captures. Bracketlapse’s in-place standby mode keeps a listener running and emits a standard-output event after every fusion:

This says an HDR frame is available. Manager submits a scan request to SunsetScore’s persistent JSONL service; that service scans the directory and processes only new photos at sampling positions. For example:

Submitting scan does not wait for all scoring to finish, so capture and fusion continue. At task completion, Manager sends finalize and waits for final scanning, aggregation, and score-file writing. Sessions distinguish directories; a task and its continuous batches reuse a persistent model, reducing repeated process startup and model loading.

There are two processing granularities: complete exposure groups can be fused and scored incrementally, while deflickering and final video encoding finish after HDR production ends. Scoring can overlap processing completion; final material handling uses the complete result.

Progress comes from actual stage results

Capture, HDR, scoring, and video maintain separate progress. Video uses FFmpeg video_started, video_progress, and video_completed events containing finished and total frame counts. Completion is emitted only after a successful exit.

The interface can therefore show that capture is ongoing, how many HDR groups are done, and how many frames are encoded. Throughput still depends on exposure, downloads, CPU/GPU, and disk. Parallelism reduces waiting without promising a fixed real-time processing speed.

6. Local visual scoring and material retention

From individual scores to sunset intervals

SunsetScore uses a local Qwen3-VL model with llama.cpp. The model selects visual categories; the program maps them to scores from 0 to 5 to keep scores and reasons aligned. After initial resource preparation, scoring can run offline.

The default interval is ten photos: samples 1, 11, 21, 31, and so on. Scores mainly describe visible cloud coloration. Ordinary white clouds, a sunset alone, or a warm horizon do not meet the colorful-cloud threshold. Clearly colored clouds can reach 3; stronger color or wider coverage scores higher.

Any sample reaching 3 produces has_sunset = true. Adjacent high-scoring samples form intervals, split by low scores or failures. Average and maximum scores describe the result; the maximum also labels the album.

Using any clear sample as evidence preserves short-lived color. Hours of ordinary sky should not dilute a few worthwhile minutes. Sampling can still miss shorter changes, so adjust the interval to the capture cadence.

The score describes visual features, not probability or a photograph’s overall value. The model does not read location or EXIF time, so visually similar dawn clouds can also score highly.

Make scores produce explainable archive decisions

Manager uses analysis to decide HDR retention:

Result Handling
Colorful sunset detected Retain hdr_enfuse; append the maximum -Sx score to managed date/time albums
Successful scoring without a sunset Mark hdr_enfuse and clean it after three days
Analysis failed, or failed samples exist without a detected sunset Retain HDR and report scoring failure

Directories without a sunset receive .timelapse-hdr-enfuse-delete with a timezone-aware deadline. Manager scans auto_root on service initialization and later task-list checks, at most once a minute. It handles only valid, expired markers on hdr_enfuse. If no checks run during that period, deletion occurs during a later check.

The three-day window allows review and separate saving. This policy covers only marked HDR directories. Original photos, deflickered intermediate frames, and video follow their respective task cleanup settings.

7. Recovery, dependencies, and notifications for long runs

Keep captured material when processing fails

Capture, processing, and task completion are distinct states. If Bracketlapse exits unexpectedly during a finite capture, Manager records recovery as needed, lets the camera finish, and reruns recovery processing over the final photos with overwrite enabled.

If the finite task still fails, cleanup is skipped and originals retained. Scoring failure must likewise not count as “no sunset,” or inference faults become deletion criteria. These rules protect material before declaring task success.

After a successful download, the camera-control tool deletes the corresponding camera copy. The local download directory therefore owns original preservation, making failure and cleanup boundaries particularly important.

Make task dependencies identifiable

Manager stores workflow tools, Python environments, and scoring resources under the application’s .timelapse/dependencies/. Tasks resolve commands there, reducing differences from global PATH and other Python environments.

The Package Management page checks and installs components. For our tools exposing build information, it shows version, source branch, and build time. Camera Timelapse Controller, Bracketlapse, and SunsetScore updates can select branches, helping identify the exact tool versions a task used.

The GUI supports Windows, macOS, and Linux. Actual camera control depends on gphoto2 support for that camera and platform. The current main flow requires Bracketlapse 0.4.1 or later and optional SunsetScore 0.12.0 or later.

Review results away from the computer

A WeCom webhook sends task states, score summaries, and the highest-scoring photo. Logs diagnose the process, while notifications bring completed results to the place where I normally check messages.

The page supports text and image tests; the robot address uses a YOUR_KEY placeholder.

9. Two companion tools: detailed editing and RAW organization

Lumalapse provides RAW sequence import, exposure curves, keyframe color grading, and video export for material needing detailed adjustments. It decodes in linear space through LibRaw/rawpy, computes curves in the log2 brightness domain, and uses the difference between the smoothed target and measured curves as per-frame EV compensation, then adds manual keyframe exposure adjustments.

This combines deflickering with deliberately designed brightness changes while retaining highlight, shadow, and white-balance controls. Analysis and keyframes are cached in the material directory’s .lumalapse/ for reopening and continued editing.

NEF Filter applies JPG selection to Nikon RAW files: it finds NEFs without matching JPGs, displays the proposed deletion list, and waits for confirmation by default. It supports separate JPG and NEF directories and scans non-recursively by default, fitting post-selection organization.

Both are independent companion tools. The automated main flow handles capture through initial selection; worthwhile material can continue into more detailed editing and organization.

10. Evolution and version references

The implementation passed through three main stages: individual camera-control, bracket-fusion, and deflickering capabilities in June; a task manager, GUI, and scoring entry point in July; and incremental processing, persistent models, recovery, and delayed cleanup in August–September. Three choices summarize the resulting design: exchange complete exposure groups, record execution as independent tasks, and base archiving on explicit processing results.
