Implementing Network-Synchronized Two-Player Hand-Holding in a Game

Posted on 2026-09-01 In 游戏开发 Views:

I developed hand-holding for our social game’s 3C system: the initiator leads and the recipient follows. Both must adapt to terrain, keep their hands together, and work with personal actions and other gameplay.

Hand-holding integration test, cropped to remove the surrounding interface.

This article builds from basic following and hand contact to improvements in turning, hand poses, and network synchronization, guided by debugging and feedback.

1. Design goals and control model

Hand-holding appears to mean simply bringing two players’ hands together, but requires coordinating four systems:

  1. Interaction state: who invites, who accepts, when it starts, and when it ends.
  2. Root movement: the recipient follows the initiator across terrain, turns, and teleports.
  3. Animation: major actions stay aligned, while the recipient’s gait reflects its own actual movement.
  4. Hand IK: arms of different lengths and orientations approach a shared contact point within joint limits.

The results must also agree across initiator, recipient, and observer views. The project uses a single-authority model on the initiator:

  • The initiator owns local movement and calculates the recipient’s follow position, movement animation parameters, and shared IK target.
  • The recipient freezes local movement input and its KCC Motor, consuming the initiator’s results.
  • Observers consume the same paired snapshots and display both players at a common playback time.

Authority here identifies the source of client presentation calculations. The server maintains interaction relationships and business data; clients establish or remove control from room state. Body movement, arm targets, and animation states are managed separately so several systems do not write the same presentation result.

2. Architecture and data flow

2.1 Components and update timing

HoldHandComponent composes three controllers, dispatched externally by PlayerInteractionRuntimeComponent according to room interaction state:

Component Responsibility and update timing
HoldHandRuntimeController Maintain local interaction, freeze/restore control; calculate or consume poses after KCC updates, drive recipient animation, and broadcast
HoldHandObserverSyncController Manage observed pairs and sample a snapshot buffer shared by both players each frame
HoldHandIKRuntimeController Manage skeleton registration, shared contact, IK pauses/weights, and sending/consuming targets
HoldHandIKLateUpdateDriver Run IK in LateUpdate with execution order 10000, after animation and root updates

Movement, remote playback, and bone solving need different update times. Separating them allows personal actions to release hand IK temporarily while preserving the relationship and positional following.

3. Interaction state and lifecycle

3.1 Request and acceptance

Entry points send requests through IntimacyComponent.RequestInteractionAsync, ReplyInteractionAsync, and related interfaces. Before requesting, check the target, shared room, busy states, and restrictions such as transformations. End conflicting personal actions before inviting.

Pair validation requires matching roles, type, and partner UIDs. A pose packet’s InteractionRevision must also match the current interaction, preventing late data from another relationship from affecting this one.

3.2 Preparation and active following

State and configuration determine whether the runtime must Begin again. The diagram shows presentation phases; the start frame controls initialization:



stateDiagram-v2
    [*] --> Inactive
    Inactive --> Initializing: Room hand-holding state becomes active
    Initializing --> Following: Initiator reaches the next frame
    Following --> Initializing: Identity or configuration changes
    Initializing --> Inactive: State becomes invalid
    Following --> Inactive: Cancel, leave, or invalid state

The initiator sets m_FollowStartFrame to the current frame plus one and initializes orbit direction and broadcast timers. The recipient immediately freezes movement, disables its Motor, clears animation requests, and switches to the remote animation controller. If the partner entity is loaded, it aligns to the preparation offset and plays the teleport effect.

This one-frame gap distinguishes initialization from continuous driving. IK pairing likewise waits until the frame after first observation before entering the connected phase.

3.3 Exit and room changes

Normal cancellation uses the cancel request and state cleanup. Stop unfreezes control, restores the original Motor-enabled state and Animator, and clears snapshots, drive position, turning state, and cached animation speed. Invalid pairs also release IK.

Before changing rooms, dissolve the relationship; a failed cancellation blocks the change. On success, clear local state before stopping presentation to avoid re-entering hand-holding next frame. The outer dispatcher also stops the local runtime when a partner leaves. Large teleports within the same room are handled by positional following.

4. Positional following and movement smoothing

4.1 Design goals

The recipient should maintain suitable formation while visibly catching up naturally. It must keep up on straight runs, orbit at a controlled speed during stationary turns, use sensible heights on slopes and steps, and arrive promptly after teleportation.

These goals involve horizontal motion, orbital rotation, vertical height, and discontinuous position changes, which need separate calculations and tuning. Network buffering handles remote playback; this section explains the initiator’s authoritative position calculation each frame.

Throughout the diagrams, a red round-headed triangle represents the initiator, and a blue round-headed diamond represents the recipient. The midpoint at each icon’s feet is the character root. Crosses or hollow markers are calculated targets, not actual positions. Each group keeps its scene and scale consistent, labels before/after states as “State 1,” “State 2,” and so on, and places explanations outside the diagram.

4.2 Local offsets and distance-proportional following

Start with a simple design: place a target beside the initiator that rotates with its facing, and let the recipient approach it according to distance. This produces basic formation and following with controls concentrated in offset and catch-up speed.

4.2.1 The active follow target

Start with just two people. The initiator leads; the recipient is led. The red triangle and blue diamond identify them, with foot midpoints indicating positions.

Without follow control, the initiator walks ahead while the recipient stays put:

They drift apart, so first define where the recipient should stand.

Add a formation point. Choose a position beside the initiator, such as slightly behind on the left, and mark it with a cross. The point moves with the initiator. Placing the recipient directly there every frame gives the simplest following:

This preserves formation but makes the recipient feel attached rigidly to the initiator, without a natural catch-up motion. A sudden target change also causes an immediate jump. The next subsection keeps the same point and changes only how the recipient reaches it.

Express formation as a character-relative offset. Lateral and forward/back distances define the point and follow the initiator’s position and facing. FollowOffset describes this: about 0.82 m left and 0.17 m behind creates a slightly staggered side-by-side formation, consistent across facing directions.

Entry also uses PreparationOffset for a one-time alignment; active following uses FollowOffset. Preparation and continuous pursuit serve different purposes:

4.2.2 A spring model

Let the recipient catch up frame by frame. Instead of directly aligning each frame, advance a small distance from its own position. Farther means faster; nearer means slower, as if a spring connected it to the target.

The spring coefficient sets catch-up strength at a given distance. The blue arrow is this frame’s step, also dependent on elapsed time: at the same speed, a shorter frame produces a smaller step. Each result becomes the next frame’s drive position.

Distance-only speed has two limits: a large gap can produce excessive speed, while a small gap can converge too slowly.

Add minimum and maximum speeds. Small gaps still get sufficient pursuit, while large gaps cannot increase speed without bound:

Limits make pursuit easier to configure, but minimum speed can still produce oversized steps near the target. A basic implementation snaps within a stop radius to finish alignment; section 4.6.1 addresses the resulting fixed-distance discontinuity.

MoveTowards advances using speed and frame duration, stopping at the target when the frame budget reaches it rather than overshooting. The diagrams explain distance and steps, not a scale simulation of the example values below.

This spring is not a strict second-order physical spring. It is an engineering model of distance-proportional speed, limits, and bounded movement, without mass or damping parameters, making stable behavior easier for designers to tune.

Crucially, m_DrivenPosition does not read the remote recipient entity’s interpolated position. Packet delay can leave that entity behind; reusing it as the next starting point feeds network jitter back into authoritative calculation and creates an increasingly unstable feedback loop.

4.2.3 Basic behavior and tradeoffs

The recipient can now remain near the initiator and catch up during movement. This has two immediate benefits:

  • Local offsets naturally preserve relative formation with simple rotation and movement logic.
  • A bounded spring avoids teleporting for one snapshot error, with independently tunable speed limits.

Sharp turns, rapidly crossing obstacles, or server corrections inevitably create pursuit lag. (That is not necessarily a drawback: rigid positional motion would not feel like one person leading another.)

Basic following therefore does not require the recipient to be pinned to the target at every moment. Some lag conveys being led. The next improvements concern sharp-turn speed and terrain adaptation, keeping pursuit natural.

4.3 Speed and height problems in playtests

Local offsets and distance-proportional speed preserve formation, but the initiator’s turn rotates the entire offset immediately. A sharp stationary turn sends the target quickly to the other side and can make pursuit feel like being flung around. Simply reducing follow speed also affects ordinary walking and running.

Tuning could not easily satisfy both running and sharp turns. Speed sufficient to keep up with walking/running produced overly fast orbiting. Lower speed softened turns but eventually failed to keep up with runs. Straight pursuit and turning shared one speed constraint; they needed separate handling rather than repeated adjustment of one number.

Further playtesting revealed two related problems: fixed height offsets could bury the recipient in the ground, and stationary turns could leave it in Idle while sliding sideways. Orbit targets, ground height, and animation from actual movement all needed adjustment together.

4.4 Separate horizontal pursuit from orbital rotation

To preserve pursuit while independently tuning turns, I split horizontal following, orbital rotation, and ground height. Distance-proportional following still approaches the target; independent rotation state determines its orbit; ground probing handles height.

First consider an instantly rotated target. Behind-left is relative to the initiator’s facing. If the initiator suddenly turns right and the target immediately adopts that direction, it jumps to the other side:

The spring sees a larger gap and accelerates the recipient. Lowering pursuit speed softens turns but can undermine normal running.

Let the formation point orbit frame by frame too. Keep spring pursuit but change target motion: after the turn, the point gradually moves around the initiator. Each frame updates the target first, then advances the recipient from its previous position.

The black dashed line is the target’s traveled path, and the blue solid line the recipient’s actual path. The blue dashed arrow points toward this frame’s not-yet-reached target:

The model has grown from two independent characters into spring pursuit of a smoothly orbiting target. The recipient still advances in bounded straight steps each frame; many small steps form the actual trajectory.

To distinguish both paths, these flat-ground diagrams use a pursuit coefficient of 8 and speeds of 0.2–0.6 m/s. Rotation smoothing stays at 0.2 s, angular speed at 180°/s, and stop radius at 0.05 m. They follow code update order at 60 fps without networking or collision. Actual resource settings pursue more tightly, so the paths usually lie closer together.

Handle height separately through the ground. Earlier diagrams show level terrain. Pitch or roll can give the rotated offset a vertical component, pulling the recipient off the ground. Keep only the horizontal offset first, placing the target at the initiator’s height; then handle grounding or airborne following:

The blue rotated offset comes from transforming the local offset by the formation-reference rotation. Removing its vertical component gives the red horizontal offset. This reference is specifically for the formation point and smoothly catches up with the initiator’s turn; section 4.6.2 distinguishes it from recipient body facing.

PreparationOffset and FollowOffset use two horizontal components for lateral and longitudinal distances. Preparation places the recipient one meter behind; active following targets about 0.55 m left and 0.22 m behind. The direction is orbit-smoothed, projected horizontally, then given grounded or airborne height. The recipient’s body faces the initiator’s direction.

Movement still begins from the initiator’s stored drive position. Distance selects a speed within limits, the stop region gradually reduces it, and frame duration determines the step. Stop when reaching the target; a zero stop radius omits this extra deceleration.

Distinguish when distance is measured: with grounding allowed, temporarily set target height to drive height, advance using horizontal distance, then probe the ground. Without grounding, pursue using three-dimensional distance including height. Excess-distance teleport checks occur before this height adjustment and always include height difference.

4.6 Movement and smoothing improvements

4.6.1 Continuous deceleration in the stop region

Minimum speed preserves pursuit strength but can still overshoot the desired step near the target. Snapping when close finishes alignment but creates a jump that does not shrink with frame duration.

Add only a deceleration region: once inside, a smaller remaining gap means lower speed, so the final approach also completes frame by frame:

A larger StopRadius starts extra deceleration earlier. Minimum speed applies before this reduction, so actual speed inside can fall below it. Spring coefficient, speed bounds, and radius together determine pursuit and settling. Zero radius omits extra deceleration.

MoveTowards combines speed with frame duration. It reaches the target only when this frame’s step can cover the gap, keeping small-distance movement time-bounded even at high frame rates.

The drive position comes only from the authority’s own calculation, never the already-interpolated remote entity, preventing network jitter from feeding back into pursuit.

4.6.2 Orbital lag and angular speed limits

Section 4.4 separated target orbit from recipient pursuit. One distinction deserves clarification: movement direction and body facing are different. Position pursues the target, while body facing directly follows the initiator, so they can differ during turns:

followRotation determines where the formation point orbits. It is a reference for calculating formation: when the initiator has already turned but this reference is still catching up, the point moves gradually around it. It does not directly set recipient body rotation.

Gradual turning alone is insufficient; sharp turns still need response control. Rotation smoothing shapes catch-up, and maximum angular speed caps each frame’s actual turn. Current RotationFollowSmoothTime is 0.2 s and MaxRotationFollowSpeed is 180°/s.

Each frame follows this order:

  1. Read this frame’s initiator yaw change and accumulate the unconsumed angle.
  2. Consume it with SmoothDamp, then bound the actual angle by frame duration to obtain formation-reference rotation.
  3. Transform FollowOffset with that reference to produce this frame’s formation point.
  4. Measure from the stored drive position to the target, determine the step from distance-proportional speed, limits, and stop-region deceleration, then call MoveTowards.
  5. Correct height according to grounding conditions and apply recipient position; use initiator rotation directly for body facing.

For comparison, simulating the same stationary 90° right turn at 60 fps with current resource settings gives a maximum target–recipient gap of about 6 mm. Section 4.4 deliberately slows pursuit to clarify update order. Actual gaps depend on the balance of linear pursuit and angular limits.

m_AngularVelocity stores smoothing velocity; m_LagAngle stores unconsumed angle. Continuous turning retains orbit direction without accumulating full revolutions to catch up. After about 0.05 s without turning, it settles by the nearest route. Reversal also limits residual angular velocity pushing the target away. Zero smoothing time or maximum orbit speed uses initiator facing directly.

This separates linear pursuit speed from target orbit speed. Running retains enough catch-up ability while turning moves the target at a controlled angular speed. Visible lag depends on the relative constraints during the current action.

4.6.3 Grounding debounce and landing-height limits

The simplest height handling reuses initiator height. On slopes, the ground beneath each player differs, leaving the recipient floating or buried.

Cast downward from above the recipient and correct its height to the hit ground, while keeping spring-controlled horizontal motion:

This handles ordinary slopes, but edges can repeatedly change grounded state, and rays can hit high platforms or deep ground. Add state debounce and landing-height limits separately.

Recipient grounding is allowed when the initiator is stably grounded, KCC permits snapping, and the height difference is within limits. Advance horizontally first, then probe downward.

At step edges, grounding may alternate. HoldHandGroundSnapDebouncer requires a candidate state to persist before switching. Current debounce is 2 s and maximum height difference 0.5 m. Exceeding that difference immediately disables grounding without waiting.

After a ray hit, also check its height relative to the initiator. This hard limit prevents already-enabled grounding from snapping the recipient to a high platform or deep surface.

4.6.4 Align KCC and camera sampling phases

If following reads physics positions while the camera later reads interpolated display positions, the body and camera use different phases in one frame. Align the order: update character display positions, calculate following, then sample the camera.

Authoritative calculation and recipient application both happen in OnKccUpdateDone, using KCC-interpolated display positions before camera sampling. Body, target, and camera then share a phase, avoiding jitter from mixing fixed-step motion with render frames.

On the initiator’s client, the recipient entity directly applies per-frame results, avoiding stacked local-follow and network-playback smoothing.

4.6.5 Reset smoothing after teleportation

Spring pursuit suits ordinary movement, but teleportation can suddenly separate the pair too far for slow catch-up. Add a threshold: beyond it, align directly to the new formation and restart following there.

The dashed circle is a cross-section of the 3D threshold sphere. Teleport threshold is FollowTeleportDistance; pursuit distance is the 3D gap from drive position to target. The height marker emphasizes vertical displacement. Exactly reaching the threshold still uses ordinary following.

When drive-to-target distance exceeds 8 m, use the new formation under the initiator’s current facing, reset orbital angle, grounding debounce, and recipient animation speed, and immediately broadcast a Teleported result.

Teleportation is discontinuous movement. Clearing smoothing caches prevents drifting along the old direction or slowly crossing a large gap. The networking section describes corresponding remote-buffer resets.

4.7 Connecting actions during integration

After adding rotation solving, I used demonstrations and actual play with designers to verify orbit behavior, then checked walking, running, and stationary turns. The focus was whether body facing and gait connected naturally once target motion became steadier.

Orbiting also turns the recipient’s body. Keeping Idle would make it slide while standing. Body facing therefore still follows the initiator, while movement animation uses the recipient’s own actual velocity, described in section 5.

4.8 Comparing both follow designs

Both use the initiator as the calculation source and retain a separate drive position for the recipient. They differ mainly in target generation, speed allocation, near-target behavior, and terrain handling.

Design point Local offset and proportional pursuit Separate orbit and horizontal pursuit
Target turning Offset rotates directly with initiator facing Smooth offset direction separately and bound angular speed
Speed tuning One pursuit configuration affects straight motion and orbiting Configure linear pursuit and angular orbit speed separately
Near target Snap inside the stop radius Continuously decelerate with time-bounded displacement
Height Full 3D root-transformed offset Separate horizontal offset and height; debounce grounding and limit landing height
Large changes Pursue at configured speed Align beyond a threshold and reset motion/smoothing

Local offsets and proportional speed already express paired following. When natural turns, complex terrain, and stable frame-to-frame behavior matter, separating constraints provides clearer tuning control.

5. Animation synchronization and parameter smoothing

5.1 Design goals

Both players should share major action semantics—walking, jumping, gliding—while recipient gait matches its own displacement. It may orbit while the initiator turns in place or keep catching up after the initiator stops.

The animation system must reserve control for holding, harvesting, one-handed operations, and personal actions, preventing hand-holding mirroring from overwriting them.

5.2 Design and principles

The initiator supplies snapshots of mirrorable layers and derives recipient velocity from its solved horizontal displacement each frame. Transforming velocity into initiator-root local coordinates produces SpeedPerc_XZ, SpeedPerc_LocalX, and SpeedPerc_LocalZ for the recipient’s movement blend tree.

Ordinary grounded Move/Idle uses recipient speed, while jumping and gliding retain initiator action states. Broadcasts carry recipient-specific snapshots; remote clients consume them directly so all three views use the same speed source.

5.3 Animator integration and modules

5.4 Animation smoothing and compatibility

5.4.1 Advance velocity filtering only once

Ground-height changes must not count as running. Remove displacement’s Y component, cap velocity at MaxFollowSpeed, then apply exponential smoothing with AnimationVelocitySmoothTime = 0.1 s:

\[\alpha=1-e^{-\Delta t/\tau},\qquad \bar v_{next}=\operatorname{Lerp}(\bar v,v_{raw},\alpha)\]

Update this velocity only once after the initiator solves movement each frame. Animation layers and broadcasts only read it, so layer count and send frequency do not alter filtering speed. This suppresses gait jitter from SpeedPerc fluctuations.

5.4.2 Start/stop hysteresis and teleport reset

Start and stop thresholds are 0.1 m/s and 0.05 m/s. Stopping checks both raw and smoothed velocity to reduce toggling near rest. Teleportation clears velocity and movement flags so a large displacement is not interpreted as fast running.

The base layer refreshes at an independent interval, allowing recipient pursuit or orbit animation to keep updating even while the initiator is idle.

5.4.3 Yield to operation layers and personal actions

ShouldMirrorAnimationLayer excludes recipient upper-body, one-hand, two-hand, Base_1, and personal-action display layers, preserving their own driving sources.

Supported personal actions increment an entry counter, pause hand-holding IK and associated music, and restore the local Animator controller when needed. When the final personal action ends, restore the hand-holding controller and held-item presentation. An operation occupying the recipient’s right hand temporarily zeros that side’s IK weight so the operation animation controls the arm.

6. Hand IK

6.1 Design goals

Hand IK brings the initiator’s left hand and recipient’s right hand together while maintaining natural shoulders, elbows, and wrists. Different arm lengths, attachment offsets, and body positions require a shared target inside both reach ranges, followed by joint-constrained bone results.

During running, jumping, and turning, contact should move stably with the pair. Gliding or personal actions that occupy the arms must release and restore it smoothly. IK changes arm presentation only; movement owns root positions.

IK diagrams retain red initiator and blue recipient icons. Each shows both participating chains: six circular nodes in total. Red and blue shoulder → elbow → wrist chains each map to LimbIK’s bone1 → bone2 → bone3. Crosses mark logical points such as palms and contact targets; dashed reference chains add no actual nodes.

These are 2D geometric explanations. Successive states preserve upper-arm and forearm lengths to show changing inputs, targets, and constraints; proportions and poses are not real-device parameter calibration.

6.2 Shared contact and reachability

Basic hand contact starts by making two arms approach the same point. Derive a preferred point from both hand Poses, constrain it by their reach ranges, and solve through Final IK LimbIK. Connection state and weight transitions complete basic hand-holding.

6.2.1 Derive a shared Pose from two contact Poses

First consider two arms and one common target. Each arm has shoulder, elbow, and wrist nodes; temporarily treat the wrist endpoint as contact. Keep shoulders fixed and adjust elbows/wrists toward one target.

Adjusting joints backward from a specified endpoint target is inverse kinematics, or IK. This produces basic contact but does not yet establish whether both arms can reach; reachability comes next.

Place both contact Poses in world space. Average their positions and use Quaternion.Slerp at 0.5 for rotation. This result, before reach constraints, smoothing, and final offsets, is the preferred Pose. Code stores it as preferredContact before constraints to reveal how later processing changes it.

Currently these inputs come from stable references captured and reconstructed in section 6.4.1, rather than freshly animated hand Poses each frame. Both sides use one contact position, adding InitiatorContactRotationOffset and RecipientContactRotationOffset separately for grip orientation.

This establishes a shared target. LimbIK’s wrist targets must still be derived from palm attachments, as explained in section 6.5.3.

6.2.2 Approximate two-segment arms with reach spheres

Both chains now pursue a common point. Move that point farther away: elbows can extend, but hands cannot stretch indefinitely because upper-arm and forearm lengths are fixed.

Add only the two fixed bone lengths, then approximate their coverage with reach spheres. The diagrams show cross-sections comparing bent and extended states:

The simplest radius sums upper-arm and forearm lengths. Bending brings the hand closer; extension reaches farther, without changing length or coverage. A palm attachment offset can shift the sphere center, so the diagram separates it from the shoulder. Section 6.4.2 describes another approach that reserves reach margin.

With both spheres, TryConstrainSharedContact limits the preferred point to shared space. Spheres describe reach; elbow bending direction and angular joint limits need separate handling.

6.2.3 Sphere-intersection constraints

Individual reach still does not guarantee contact: distant players can have disjoint ranges. First consider them approaching until their ranges intersect:

Red and blue dashed circles are reach-sphere cross-sections. Once an intersection exists, bring an external target back into shared reach. Without one, a compromise remains and simultaneous contact cannot be guaranteed.

The implementation selects candidates in this order:

  1. Use the preferred point directly if it lies inside both spheres.
  2. For disjoint spheres, choose a compromise along the center line according to both reach capacities and set HasSharedReach false.
  3. For intersecting spheres with an external preferred point, test projections onto individual spheres; choose the nearest candidate satisfying both ranges.
  4. If neither projection works, use the spheres’ intersection circle to project and constrain the preferred point to the shared region.

The intersection circle defines the common boundary; its radius also depends on attachment margins. This establishes geometric reachability, while elbow direction and joint rotation require additional limits.

6.2.4 Smoothing, connection state, and weights

Even with shared reach, target changes and connection switches can look abrupt. Smooth the shared target frame by frame, then handle connection boundaries and arm influence.

Smooth contact in initiator-root local space using Vector3.SmoothDamp, currently with ContactPositionSmoothTime = 0.01 s. If a shared range exists, constrain the smoothed point back into it to avoid crossing boundaries during transition. Section 6.6.2 covers the full local-space process.

A newly observed pair first passes a preparation frame. From the next frame, it connects while valid and unpaused. Gliding and personal actions disconnect IK; it resumes when every pause reason disappears.

Current UpdateConnection does not use player distance. HasSharedReach separately records simultaneous reach and does not directly end the interaction or IK connection.

Connection selects a target weight of 1 or 0. Actual weight approaches it gradually instead of making the whole arm jump instantly:

These diagrams show transition endpoints; intermediate weights advance each frame. Connection affects IK without clearing room interaction state. Maximum position and rotation weights are both 1, with 0.3 s fade-in and fade-out. Position weight controls pursuit by the chain; rotation weight controls wrist orientation. Targets go to LimbIK.solver each frame before manual solving.

6.2.5 Basic behavior and tradeoffs

Shared targets, reach constraints, and weight transitions already connect both hands. Their advantages are:

  • One contact point gives both hands a stable visual grip location, rather than independent targets.
  • Sphere intersections are inexpensive, have clear boundaries, and explicitly handle unequal arm lengths.
  • Preparation, pause state, and fading support continuous entry, release, and recovery.
  • Initiator computation and broadcasting keep results consistent without requiring recipients and observers to repeat full reachability logic.
  • Final IK LimbIK reuses existing skeletons and bend configurations at low integration cost.

This is suitable for establishing basic contact before tuning offsets and weights through playtests. Geometric reachability does not eliminate the need to inspect arm poses in motion.

6.3 Hand-pose problems during movement

Spheres express reachability, not elbow preferences, shoulder limits, colliders, or clothing constraints. Some poses invert elbows or intersect bodies. Disjoint spheres still only yield a compromise, and changing contact, bone animation, and root motion together can introduce hand swing into solving.

Aligning hands while stationary proved insufficient. Contact could fold awkwardly, movement showed stutter and hand swing, wrists sometimes bent unnaturally, and arms pulled upward during large-jump descent. Animation’s influence on solving needed control beyond contact alignment.

One clear reproduction was running into a collision: IK stayed misplaced until disconnecting and reconnecting. Hands also looked unnatural after small and large jumps. Improvements focused on stable contact/bone references that current animation could not continually redefine, plus separate shoulder, elbow, and wrist limits.

Reference-pose stability reproduction: abnormal contact on the left, re-established connection on the right.

6.4 Stable references and constrained shared targets

To preserve contact during running, jumping, and pause recovery, I retained shared targets and sphere constraints but fixed inputs to stable reference poses. Targets change only with the pair’s relative relationship; bone results receive separate joint limits and smoothing.

6.4.1 The initiator computes shared contact

Reading current animated hand contact every frame can carry arm swing or one bad pose into later targets. Instead, capture both hands’ character-relative positions and rotations when hand-holding is established.

This is local space: the reference records where the hand is relative to its character, not an absolute map position. Whole-character movement carries it along; animated wrists can swing without redefining it:

When both attachments and chains first become usable, save each contact Pose in its own root’s local space. Each frame reconstruct them from current roots, average position and rotation into the preferred Pose, then apply reach constraints, local smoothing, and final offsets. Current animation never redefines the baseline.

These diagrams show reference reading; solid chains are animation poses before IK. preferredContact is the newly formed, unprocessed preferred Pose. Reach constraints change its position but retain the intermediate rotation. Local smoothing, re-constraint, and ContactPositionOffset follow, producing shared position and independent rotations. The initiator performs the full calculation; remote clients consume local targets.

6.4.2 Intersecting both reach spheres

Using complete arm lengths can still push wrists to full extension. Palm attachments lie beyond the wrist, and orientation/contact-distance changes need margin.

Keep sphere centers at shoulders and reserve palm offsets from their radii; reserve extra contact distance when needed. Each diagram changes only one margin:

Centers use shoulders. Radius sums both bone lengths minus the palm attachment offset and absolute PalmContactDistance, leaving extension margin for wrist rotation and spacing. A nonpositive remaining radius cannot form a valid reach sphere.

The diagrams vary contact spacing to explain it; the current resource’s PalmContactDistance is zero. Intersection uses section 6.2.3’s candidates and projections. Without an intersection, keep trying with a compromise target; joint limits still protect the final arms.

6.4.3 Pair validity and connection state

IK accepts only mutually linked, same-type states with downloaded Avatars and ready skeletons. Connection starts after the first-observation preparation frame when no pause reason remains.

Gliding and personal actions use a set of pause reasons; recovery waits until all are cleared. HasSharedReach describes geometry, not whether interaction or IK disconnects. Invalid skeletons, weather transformations, and recipient right-hand operations have separate release or yield logic.

6.5 Applying Final IK and dividing modules

6.5.1 Solve each arm with LimbIK

The project uses Final IK (namespace RootMotion.FinalIK). LimbIK solves one limb. Each character prepares left and right arm solvers; hand-holding uses the initiator’s left and recipient’s right.

LimbIK uses IKSolverLimb, derived from the law-of-cosines analytic IKSolverTrigonometric. Its three-node upper-arm, forearm, and wrist chain has two bone lengths. Given an endpoint and bend plane, it computes the pose and exposes endpoint rotation and weights.

IKSolverLimb.BendModifier.Arm supplies an arm-suitable bend plane. Project modules own shared targets, network authority, pause state, and three-axis limits; the plugin solves the chain itself.

6.5.2 Bind chains and update manually

EntityBaseHead.InitializeHoldHandIK uses G_LweaponTransform and G_RweaponTransform as contact attachments. Traversing upward yields wrist, forearm, and upper arm; validation precedes solver creation. Core setup is:

Disable LimbIK’s automatic component update, set targets with SetIKPosition and SetIKRotation, then manually call limb.solver.Update() at the controlled phase. This solves after animation and applies limits afterward, avoiding independently scheduled updates.

fixTransforms = false gives project code control of reference-pose restoration; target = null means writing target Poses directly without a target Transform. An invalid attachment, chain, or LimbIK prevents valid registration.

6.5.3 Convert palm targets into wrist targets

Earlier contact was simplified to one endpoint. In the plugin, the endpoint is the wrist, but gameplay aligns palms. Treating palm contact as a wrist target ignores the attachment offset.

Keep the palm target fixed and change grip orientation: as the offset rotates, the wrist must move to keep the palm on target.

First cancel the attachment’s wrist-local rotation to derive wrist orientation. Scale the local attachment position by character scale, rotate it into world space with that orientation, and subtract it from the palm target to obtain the wrist target.

The diagram enlarges offsets for clarity. ContactTargetToHandTarget takes the contact Pose, contact.localRotation, contact.localPosition, and wrist lossyScale. Only the derived wrist Pose goes into LimbIK. PalmContactDistance is applied beforehand.

6.6 IK stability and smoothing improvements

6.6.1 Fix reference poses to isolate animation disturbance

Running swings and jumps continually change bones. Extracting a new baseline every frame changes targets and limit references, potentially carrying an abnormal pose into the next solve.

Save local contact Poses per pair and arm reference rotations at the first valid solve separately. Contact follows roots; chains solve from stable references. Temporary pauses such as gliding retain them. Pair rebuilding or invalid skeletons reset them through lifecycle handling.

6.6.2 Smooth contact in character-local space

Stable references reduce arm-swing disturbance, but relative motion can still make shared contact jump. World-space smoothing would also make targets trail whole-character movement and jumps.

Smooth only changes relative to the initiator: overall displacement carries the target immediately, while relative changes converge gradually.

Apply SmoothDamp in initiator-root local space with 0.01 s smoothing, then transform back to world space. Only relative changes are smoothed; whole-character movement and jumps carry the target immediately, avoiding world-space lag.

The diagram initially shows only local target and smoothed contact. Reach constraints and configured offsets add two steps:

With shared reach, project the smoothed result back into that region. Then add root-rotated ContactPositionOffset, currently (-0.04, -0.31, -0.01). Do not write the offset into the smoothing cache, preventing accumulation or later smoothing from overwriting it. It may move the target outside reach, so tune it alongside bone limits.

Remote IK targets are also smoothed in initiator-local space and reconstructed using the locally displayed root. Section 7 explains their consumption.

6.6.3 Three-axis limits and preventing reverse elbow bending

Shared contact determines where hands go, and reach determines whether they can arrive. Neither guarantees natural joints. Add separate shoulder, elbow, and wrist ranges and prevent reverse bending: solve IK first, then constrain final bones.

HoldHandArmRotationLimits supplies yaw, pitch, and roll ranges separately. Upper arms reference the character, elbows the upper arm, and wrists the forearm. Bone axes are calibrated at initialization; reference frames follow character or parent-bone rotation at runtime.

Shoulder, elbow, and wrist limit arcs mark constraint locations. The implementation limits all three axes; the 2D diagram explains order rather than measuring actual resource angles.

Joint configuration entry points and reference frames; actual values are listed below.

Joint Yaw range Pitch range Roll range Rotation smoothing
Upper arm -45° to 80° -90° to 10° -45° to 45° 0.03 s
Elbow 0° to 145° -5° to 5° -80° to 80° 0.03 s
Wrist -30° to 20° -45° to 45° -5° to 5° 0.03 s

The elbow must satisfy both angular ranges and the normal-flexion half-space. Calculate them together so limiting angles and then preventing reversal do not overwrite each other. An infeasible intersection must not be solved by reverse bending.

6.6.4 Joint rotation smoothing and solve order

Each joint smooths rotation in its own stable frame, currently over 0.03 s. This softens small solver jumps while immediately passing character turns and parent-bone rotations to the arm.

After smoothing, apply hard three-axis limits and cache the constrained rotation, preventing the filter from accumulating error beyond limits. One arm update follows:

  1. Save the animated pose, restore stable references, and solve the complete IK pose with LimbIK.
  2. Apply the overall maximum rotation from the reference pose, then blend with animation using position/rotation weights.
  3. Recompute palm offsets from the blended wrist orientation and run LimbIK to correct contact.
  4. Smooth and constrain shoulders, elbows, and wrists, including elbow-reversal protection, producing this frame’s bones.

Do not run IK again after the final limits. When contact precision conflicts with joint ranges, prioritize joint constraints and allow a small palm gap.

6.6.5 Weight transitions and yielding to operations

Connecting and disconnecting alone do not cover personal actions. An operation can temporarily occupy one arm while the relationship remains active; simultaneous bone writers would overwrite each other.

Add pause/recovery: let animation control arms during pauses, retain this interaction’s references, and gradually restore weight toward those same references afterward.

Connection advances weights through MoveTowards, with 0.3 s fade-in/out and maximum position/rotation weights of 1. Weighted animation/IK blending gives continuous entry, pause, and recovery.

A set of pause reasons prevents one system’s release from overriding another’s occupation. A recipient operation using the right hand temporarily zeros that side’s position and rotation weights. Weather transformations or missing skeletons release IK through their own paths.

6.7 Pose adjustments and retesting

Fixing solve references to entry bone poses improved hand swing during movement. Retests with designers continued examining small lateral shakes, jumps, and collision recovery rather than judging only stationary or straight movement.

Remaining elbow poses and standing slides were handled separately: joint limits and smoothing own bone presentation; actual-speed-driven animation owns gait. Each change corresponds to a specific experience problem.

6.8 Comparing both hand-solving approaches

Both let the initiator determine shared contact and use LimbIK for local chain solving. Additional handling concerns reference poses, target smoothing, and bone constraints.

7. Network synchronization and playback smoothing

7.1 Design goals

Networking must present the initiator’s paired results stably to recipients and observers, balancing latency against arrival jitter that causes body stutter, stretched player spacing, and jumping hand targets.

Position, animation, and IK change at different rates. Tune their streams independently; they share interaction identity and authority but retain their own consumption and smoothing.

7.2 Design and data model

The initiator sends paired poses, animation snapshots, and IK targets through NetworkServiceComponent. Paired-pose fields include:

Field Purpose
Both UIDs and interaction type Identify the pair and validate room state
Both positions and rotations Two root Poses from the same sample
SampleTime Initiator’s monotonic sample time for ordering and velocity estimates
InteractionRevision Check that the snapshot belongs to this interaction
Teleported Clear old trajectories and rebuild the buffer baseline

SampleTime compares only differences from one sender and requires no client clock synchronization. Each recipient or observer maintains its own playback time and samples both poses from one paired buffer.

Independent IK broadcasts carry two local target Poses, Sequence, BlendWeight, Connected, and HasSharedReach. Animation carries initiator-generated recipient movement parameters so remote clients need not infer gait from network displacement.

7.4 Networking and smoothing improvements

7.4.1 Share one sample time for both players

First consider displaying each received position immediately. Messages are discrete; without updates between them, the view pauses and jumps when the next arrives:

Fill intermediate states between adjacent positions. Save previous and next positions and display intermediate values each frame: interpolation. Knowing the next position requires delayed playback, adding a little display latency:

Give both players the same playback time. Independent interpolation can still stretch their spacing through different progress. Put poses from one calculation in a paired snapshot and sample both from one timeline.

Sample time records when the initiator captured positions, arrival time when the packet reached this client, and playback cursor which instant is displayed. Both players share that cursor:

HoldHandSnapshotBuffer retains at most 64 paired snapshots. Between samples, positions interpolate linearly and rotations spherically. Both players always use one playback time, preventing independent trajectory errors from accumulating into arm separation.

Three timelines show sender sampling, local arrival, and buffered playback. Arrivals may be uneven, but the cursor advances continuously and both players sample the same instant. Bottom icons represent sampled results, not map formation. Motion speed and interpolation progress use sender time.

View Playback Interpolation delay Maximum extrapolation
Local initiator Apply authoritative per-frame results directly No network buffer Unneeded
Local recipient Apply both poses at one time after KCC update 0.06 s 0.03 s
Observer Pair controller samples/applies both each frame 0.09 s 0.1 s

Longer buffering absorbs more jitter but adds latency. Recipients and observers therefore have separate delays and extrapolation limits.

7.4.2 Continuous playback time and small speed corrections

Playback advances using continuous local time while targeting a delay behind the latest sample. When buffer depth deviates by more than one position interval, about ±5% playback-speed correction reduces drift, instead of repositioning on every packet.

Even several packets in one frame cannot repeatedly jump playback progress. After long main-thread stalls or excessive lag, realign time to the latest sample minus configured delay and clear corrections.

7.4.3 Bounded extrapolation and prediction-error decay

During packet gaps, estimate velocity from the last two sender sample times and advance only for the configured duration. Extrapolate horizontally at at most 20 m/s; hold latest height and rotation to avoid amplifying ground snaps or guessing turns.

When a new sample corrects the predicted trajectory, record prediction differences at the same playback time and exponentially decay position/rotation error each frame. Correction takes max(0.05 s, interpolation delay), preserving continuity on arrival while returning gradually to authority.

Explicit teleportation, large jumps, or sample gaps beyond resynchronization clear old trajectories and errors and rebuild the baseline. The current gap threshold is 1 s. If no sample arrives by the extrapolation limit, prediction stops.

7.4.4 Tune the three streams independently

DataHoldHandControl centralizes synchronization parameters. Current periodic settings are:

Stream Interval Content and strategy
Paired poses 0.1 s, about 10 Hz Both roots, sample time, revision, and teleport flag
Recipient base-layer refresh 0.2 s, about 5 Hz Continuously update grounded movement parameters; ordinary animation requests may also trigger sends
IK targets 0.2 s, about 5 Hz Both local targets, weights, and connection state; smooth each frame remotely

Separate rates balance bandwidth, latency, and precision by responsibility. Teleports trigger immediate pose and animation broadcasts; recipient reporting reuses ordinary player mechanisms. These are periodic settings, not guaranteed arrival intervals.

7.4.5 Reject stale data and duplicate driving

Pose receivers validate mutual linkage, type, sample time, and InteractionRevision; buffers reject non-increasing sample times. IK compares wrap-aware Sequence values to reject duplicates and out-of-order targets.

Ordinary player packets can update caches but cannot override active paired-pose control. Recipients apply both sampled poses together, and initiators drive their local recipient entities directly, avoiding additional smoothing of the same trajectory.

Poses without sample times use target smoothing: recipients consume targets through SmoothDamp and use relative anchors for partners; observers smooth both targets separately. Valid SampleTime selects the timeline buffer described here.

7.4.6 Synchronize and reconstruct local IK targets

Sending a world-space grip directly can leave hands at the last received point while interpolated bodies move ahead. Misaligned update timing makes hands appear to trail behind.

Instead, record position and rotation relative to the initiator. Remote clients smooth relative changes, then reconstruct targets using currently displayed character roots:

The initiator sends root-relative IK positions and rotations. Remote clients smooth locally, reconstruct world targets using displayed roots, and pass them to both LimbIK solvers.

The diagrams show translation; rotation uses the same root transformation. Remote target/weight smoothing takes half the IK interval with a 0.01 s minimum, currently 0.1 s. Overall root movement passes directly to targets; filters handle relative pose changes.

Remote clients run their own LimbIK and joint limits, not shared-sphere solving. Arms are released before the first IK packet. A valid pair receiving no further packets keeps consuming the last target. There is currently no independent IK timeout; pose extrapolation limits do not provide that protection.

7.5 Retesting observer views

After improving third-party stutter, designers and I retested on the previously problematic devices and confirmed better movement continuity for observers.

The question was whether observers continuously see both players moving together. Local authoritative position and arm calculations must be stable, while remote snapshot playback must tolerate arrival jitter to convey the same following experience.
