Organizing Game Logs, Starting with 947 Repeated Messages

Posted on 2025-06-12 In 游戏开发 Views:

Frequent logs can obscure production issues. I counted messages from game entry until five seconds after the frame rate stabilized.

The top message appeared 947 times; the next few appeared dozens of times. Removing it noticeably improved perceived smoothness, prompting a review of log frequency, purpose, and switches.

Define the sampling window first

The 947 occurrences do not mean “947 per second” or “947 in the five seconds after stabilization.” The sample covered the whole entry process and continued for five seconds after the frame rate stabilized.

Without a clear window, the same number can suggest different performance conclusions. My question was which messages repeated conspicuously during a common entry flow and deserved investigation first.

Redrawn from the original statistics screenshot, retaining counts while replacing internal function and module names with descriptions of their purpose.

Aggregate by a fixed event or log template where possible. If a message embeds a timestamp, object ID, and position, every string differs; grouping by the full text can hide repeated calls.

High frequency does not always justify deletion

Counts only identify leads. Network connections, critical resource loading, and exceptional states may remain valuable for production diagnosis even when they appear frequently during entry.

I checked each message’s purpose, whether a normal flow still needed it, whether it could be enabled by module during investigation, and whether a simpler expression would suffice.

Repeated process logs left over from early development can be removed or disabled by default. Useful diagnostic details should retain a switch. Logging once per state change is usually easier to read than repeating the same state every frame, but equivalence depends on what needs to be observed.

Hidden output can still cost time

Logging costs can arise from parameter preparation, string formatting, Lua-to-C# calls, stack collection, and subsequent output and display.

Console collapsing or filtering does not mean those earlier steps never happened. If a string is already built before reaching the logging function, disabling output inside that function cannot eliminate construction costs.

Lua concatenation has the same issue. Macros, conditional methods, or lazy construction are other options, but first establish where the project’s logging layer filters messages. Otherwise, you may optimize only presentation.

Levels and module tags address different questions

Log levels express importance; module tags identify the source. Use them together: for example, inspect Debug messages from the resource module while retaining Warning and Error messages from other modules.

For frequently investigated modules, disable detailed logs by default but provide an explicit way to enable them. Normal use stays readable, and integration testing no longer requires adding temporary print calls everywhere.

Tag design should also be maintainable. Requiring repetitive handwritten wrappers for each new module can lead to inconsistent spelling or callers bypassing the common entry point.

July 2026 addition: generate code for log tags

In another project, I later organized tag integration: add an entry to a central definition, then generate the corresponding template code through an editor menu.

This provides a fixed place to add or remove tags and makes filtering frequent output by module easier. It addresses maintenance of logging entry points, but does not automatically fix argument-evaluation costs at every call site. Calls preparing expensive content still need review.

What this record demonstrates

The original statistics retain output counts and my experience after removing the frequent message, but lack a complete frame-time comparison on the same device and scene. I therefore cannot turn this record into a claim of a specific percentage performance improvement.

To quantify the benefit, fix the entry flow and sampling conditions, then compare CPU time, allocations, and frame-time distributions with logging enabled and disabled. Editor Console behavior is not a substitute for results on a real device.

The most useful outcome was turning “too many logs” into individually actionable items: a defined sampling window, identifiable high-frequency sources, diagnostic information worth keeping, and ways to enable it again later.
